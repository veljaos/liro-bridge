# Phase F11 — PKCS#11

**Prerequisite reading:** `docs/SPEC.md` in full, `docs/decisions.md` in full. F2's own phase document for what `keysource` is and why it looks the way it does.

**Prerequisite phase:** F10 complete. The program installs, updates, signs, and has been installed by someone other than its author.

**Goal of this phase:** a card that Windows CNG cannot use is signed with through its issuer's own PKCS#11 module, over the same `keysource.Source` interface as everything else.

**Explicitly not in this phase:** no macOS, no Linux, no new window, no protocol change, no packaging change. The PDF engine, the consent flow and the audit log are untouched.

---

## 0. What this phase is for, stated before anything technical

Three issuers matter in Serbia and the agent's position with each is different:

- **MUP e-ID.** CNG handles it today. It is what every measurement in this project has been taken against.
- **Pošta.** SafeSign middleware. CNG may or may not see the card depending on how SafeSign was installed and which container it registered.
- **Halcom.** Nexus Personal. Same uncertainty, and no card available to test with.

PKCS#11 is the interface every one of those middlewares exposes directly, without going through Windows' certificate store. It is the answer when CNG does not see a card that is plainly in the reader.

**And it is the only road to macOS and Linux**, where CNG does not exist. F12 and F13 cannot start until this layer exists. That is the larger reason this phase is here, and it should shape the interface even though this phase ships nothing but Windows.

### 0.1 What this phase deliberately does not solve

**MUP cards on macOS and Linux.** MUP ships middleware for Windows only. There is no `.so` and no `.dylib`, so on those platforms a PKCS#11 client has nothing to load, and the card is unreachable by this route.

The answer, when it is needed, is to speak to the card directly over PC/SC rather than through anybody's middleware — the shape `srb-id-pkcs11` takes. That is a phase of its own, roughly F3-sized, and **it is not this one**. On Windows the question does not arise: CNG already handles MUP cards, and has since F1.

Record the deferral rather than leaving it implied. F12 will meet it on its first day.

## 1. Whether `cgo` is actually required — establish this first

SPEC §1 promises a single binary with no runtime dependencies, and CI builds with `CGO_ENABLED=0` in seven places. The received wisdom is that PKCS#11 means `cgo`, because the common Go bindings use it.

**On Windows that may not be true.** A PKCS#11 module is a DLL with a documented C ABI and one entry point, `C_GetFunctionList`, which hands back a struct of function pointers. `golang.org/x/sys/windows` can load a DLL and call through those pointers without a C compiler anywhere in the build.

So, before writing anything:

- **Establish whether the whole of this phase can be done with `CGO_ENABLED=0` on Windows.** Load a real module, call `C_GetFunctionList`, and get a real answer back from a real card. If it works, SPEC §1 survives this phase untouched and CI does not change.
- If it cannot — say precisely what forces it. Not "the bindings use cgo": which call, and why it cannot be made through a function pointer.
- **Do not reach for a third-party PKCS#11 binding before answering this.** The question is whether this program needs a C toolchain, and adopting a dependency that assumes the answer is the way to never find out.

If `cgo` turns out to be unavoidable, **stop and say so before building on it**. That is an amendment to SPEC §1 and the owner's to make, not a consequence to discover in a report. It also drags in a cross-compilation toolchain for three platforms, which is the largest single cost in this phase and must be priced before it is paid.

Whichever way it goes, record it with the measurement that settled it.

### 1.1 A thing that changes if cgo arrives

`-race` needs `cgo`, and the development machine has no C compiler, so `cmd/liro-bridge` has never been race-checked anywhere (recorded in F10's handover). CI's Ubuntu job races `internal/cli` only. If a C toolchain enters this project, that gap becomes closeable — and the package holding the windows, the timers and now a foreign DLL's threading model is exactly where a race would live. Note it; don't fix it here.

## 2. The client

One new backend under `internal/keysource/`, beside `windowscng` and `softtoken`, implementing `keysource.Source` and `keysource.Session` identically. Nothing above that layer learns a new word.

That interface is small and this phase does not widen it:

- `List` returns every certificate the module can sign with, including unusable ones with their reason.
- `Open` begins a session and may prompt for a PIN.
- `SignDigest` signs a pre-computed digest.
- `Certificate` and `Chain`.

**`Chain` is where PKCS#11 differs and it must be handled honestly.** CNG can often supply the issuing chain; a PKCS#11 module frequently cannot, because the issuer's certificate is simply not an object on the card. The interface already says the chain may be empty and the caller completes it (SPEC §11.6). Return what is there, never a guess, and say in the report what the modules you tested actually gave you — because B-LT depends on it and a missing chain becomes a missing signature level, not a missing field.

### 2.1 The mechanism matters

`SignDigest` takes a digest, not a document. The mechanism handed to `C_Sign` must produce a signature over exactly the bytes the rest of this program expects, and the two usual choices are not equivalent:

- `CKM_RSA_PKCS` expects a pre-built DigestInfo and signs it.
- `CKM_SHA256_RSA_PKCS` expects the *data* and does the hashing itself, which is wrong here because the digest is already computed.

Get this wrong and the signature verifies against nothing while every layer reports success. **Verify with the independent verifier of SPEC §16.4** — the one that recomputes the `/ByteRange` digest and compares it — not by checking that a byte array came back.

SPEC §18.8's prohibition applies without exception: no SHA-1, no MD5, whatever the module offers.

## 3. Finding the module

A PKCS#11 module is a file on disk that somebody else's installer put somewhere. The agent has to find it or be told where it is.

- **Establish where each issuer's installer actually puts its module** — read it off this machine for SafeSign, and say plainly for Nexus that it was not verified if no installation is available.
- **Configuration takes a path.** A person who knows where their module is must be able to say so, in Settings, and have it used. That is the escape hatch for every installation this phase did not anticipate.
- **Never load a module from a path the protocol supplied.** A calling application naming a DLL for the agent to load is arbitrary code execution wearing a configuration field. The path comes from configuration or from discovery, and from nowhere else.
- **A module that fails to load is not a crash.** Say which path, say the module did not load, carry on with the sources that did. SPEC §7's vocabulary needs a code for it if none fits.

## 4. Which source signs

On Windows, two backends can now see the same card, and the agent must not offer the same certificate twice.

Decide and record:

- **CNG stays the default on Windows.** Every measurement in this project was taken through it and F10 shipped on it. PKCS#11 is what runs when CNG does not see the card, or when the person has configured a module explicitly.
- **What the certificate list shows when both see the same card.** One row, not two. The thumbprint is the same certificate either way; deduplicate on it and say which source won.
- **What the audit log records.** SPEC §6.7's entry says what was signed and with what; if it does not currently name the backend, decide whether it should. A signature made through a PKCS#11 module and one made through CNG are the same signature, but they are not the same event.

## 5. The PIN

SPEC §6.5 is the most important paragraph in the specification and it does not bend here. The agent never sees the PIN.

PKCS#11 makes that harder than CNG does, because `C_Login` takes the PIN as an argument. Two arrangements exist and the difference is not cosmetic:

- **Protected authentication path** — the module or the reader collects the PIN itself and the agent passes `NULL`. This is what SPEC §6.5 describes and it is what to use wherever the module supports it.
- **The agent collects it and passes it in** — which means the PIN exists in this program's memory.

**Establish which each tested module supports**, and if any module offers only the second, stop and raise it rather than building a PIN box. That is a change to the promise the specification makes, not an implementation detail.

Whatever happens: never log a PIN, never include one in an error, never put one in a crash dump, and never keep one after `C_Login` returns.

**And the retry counter.** Three wrong PINs block a card; for a national identity card, unblocking means a visit to a police station. Nothing in this layer retries a PIN automatically, ever, for any reason — the same rule `docs/CLI.md` states and F8 §4.4 states to SDK users.

## 6. Testing, and the hardware that exists

Available: a MUP e-ID card and a Pošta card. **No Halcom card.**

So:

- **The exit condition is the Pošta card, signed through SafeSign's PKCS#11 module rather than through CNG**, with the resulting PDF verified by the independent verifier and by one external tool. That is a real card, a real module, and a card this project has never signed with.
- **Halcom is written, not verified.** Say so in the report, in `README.md`, and in the entry. An untested issuer claimed as supported is the defect; an untested issuer named as untested is honest.
- **The soft token stays the CI story.** Nothing in this phase requires a card to run in CI, and nothing in this phase may make the soft-token path harder to reach.

`softhsm2` is worth considering as a CI-testable module — a real PKCS#11 implementation that needs no hardware. If it can run on the Windows runner, this layer gets covered by CI rather than by one person with a card. Establish whether it can before deciding it cannot.

## 7. `srb-id-pkcs11`, and what it is for

`github.com/ubavic/srb-id-pkcs11` is a PKCS#11 module for the Serbian e-ID, in Zig, under the Unlicense. The licence imposes nothing.

**It is reading, not a dependency and not a source of code.** Its value is `src/smart-card.zig`, `src/apdu.zig` and `src/operation.zig`, which document the APDU sequence for a MUP Gemalto card — something written down nowhere else. That knowledge belongs to §0.1's deferred phase, not to this one.

Two things to note if it is ever read for more than reference: it offers MD5, SHA-1 and RIPEMD160 mechanisms, which SPEC §18.8 forbids this program from ever producing; and its own README warns it may damage a token. Neither disqualifies it as documentation. Both disqualify it as something to ship.

## Rules

This phase only. No other platform, no new capability, no protocol change, no installer change.

**Answer §1 before building on its answer.** If `cgo` is required, that is the owner's decision and it stops the phase until it is made.

**Verify signatures with the independent verifier**, not by observing that a call returned bytes. §2.1 is the reason.

Measure rather than reason. Write your predictions down before you measure. Verify by running the built binary. No synthetic input (D-094). Exact PID only. Observe the property rather than time the machine (D-201). No `//nolint`. Leave the machine as you found it, proven against your own snapshot — and note D-266: a test run writes `HKCU\…\Run` reproducibly.

Full Go suite with `-count=1` on Windows, with and without `softtoken`. The TypeScript suite on both platforms.

Record a decision for each choice above that says *decide and record*, plus whatever §1's investigation turns up.

**Report:** what `C_GetFunctionList` actually returned and from where; whether `CGO_ENABLED=0` survived and what settled it; which mechanism each module wanted and how the signature was verified; what `Chain` gave you per module and what that does to B-LT; whether the protected authentication path was available; and what is written but unverified.
