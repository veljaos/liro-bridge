# Phase F6 — Local signing

**Prerequisite reading:** `docs/SPEC.md` in full, then `docs/decisions.md` in full.

**Prerequisite phase:** F5 complete, verified against real hardware — the consent window lists certificates, the PIN dialog appears in front, a real MUP certificate produces a signed document with a visible stamp, and Adobe accepts it.

**Goal of this phase:** the agent becomes something a person uses without a command line. Drag PDFs onto it, or right-click a file in Explorer, and sign.

**After this phase the product is usable.** Everything beyond it — the HTTP protocol, SDKs, an installer, macOS and Linux — serves other people's programs and other operating systems. This is the last phase the owner needs in order to sign documents every day.

**Explicitly not in this phase:** no HTTP server, no SDK, no installer. `internal/api` remains empty.

## Part 0 — Four repairs first

Do these before starting the phase proper. Two of them are keeping CI red, and a red CI stops being read within a week.

### 0a. The Trusted List seed digest and sequence disagree

`go test ./...` fails on the owner's machine and in CI:

```
TestSeedDigestMatchesExpected
  got  d83bac89f7f851fdd5051bdb8bc029647dea66d72e8a1b3adba7bc6bb9d3e39d
  want 3f5744843bcfaba0698c6b5f7121ee9f133151249808c9de0ebb8e351d9ddb8b
```

`3f574484…` is the digest of Trusted List **sequence 36**, published by the Ministry and verified against the digest printed in the Official Gazette. That is the list the owner supplied and the one every measurement in SPEC §11 was taken from.

Meanwhile the test log shows `currentSequence=37`, while `liro-bridge certs` reports `sekvenca 36, izdata 2026-05-20`.

Three numbers that should agree do not. Establish what actually happened before changing anything:

- What sequence and digest does the embedded seed have right now?
- What does the cached list on disk have?
- Which one does `certs` report, and which does the test compare against?

Then fix it so all three agree, and say plainly what the cause was. If a newer list was genuinely published and embedded, the expected digest must be updated **and its signature verified against the pinned signer certificates first** — SPEC §11.1 makes the Trusted List the primary authority for whether a certificate is qualified, so an unverified seed is worse than a stale one.

Add a test that fails if the embedded seed's own sequence number disagrees with what the code reports.

### 0b. Windows-internal certificates still appear in `certs`

Running `certs` on the owner's home machine shows:

```
[2] 5a26d334-110e-4468-910f-34313774f081   ✗ neupotrebljiv
    Namena     autentifikacija
    Izdavalac  5a26d334-110e-4468-910f-34313774f081
    Smeštaj    softver
```

A self-signed Windows-internal certificate with a GUID for a name. A previous round hid these from the consent window; the `certs` command still lists them without `--all`.

Apply the same filter in both places. One rule, one implementation, used by every surface that lists certificates.

### 0c. The autostart test fails on the CI runner

```
TestWindowsAutostartRoundTrip
  SetEnabled(true): The system cannot find the file specified.
```

It passes on both of the owner's machines and fails on the GitHub runner, where the executable path the test expects does not exist. The feature works — the owner has seen the setting take effect.

Make the test independent of where the binary happens to live, or skip it with a clear message when there is no real installation to write. A test that fails for environmental reasons teaches people to ignore failures.

### 0d. `golangci-lint` fails in CI

The Ubuntu job fails at the lint step after 36 seconds. `golangci-lint` runs clean locally at version 2.13.2. The action in the workflow is `golangci-lint-action@v6`, which predates the v2 configuration schema the repository uses.

Update the action, pin the version to match what the project uses locally, and confirm the job goes green.

**All four repairs are done and CI is green before Part 1 begins.**

## Part 1 — Drag and drop

The main window — a placeholder since F5 — becomes the working surface.

- Accept files dropped from Explorer onto the window. Register with `DragAcceptFiles` and handle `WM_DROPFILES`.
- Show the accepted files as a list, with a count and each file's size.
- Accept a **folder** dropped onto the window: take the PDFs in it, without recursing into subfolders, and say how many were found.
- Accept files added through a **Browse** button as well; not everyone drags.
- Let a file be removed from the list before signing.
- Show a clear empty state that says what to do.

Filter to `.pdf` by extension when a folder is dropped. Do not filter a file the user dropped deliberately — if it is not a PDF, that is an error the signing step reports by name, not something silently dropped from the list.

## Part 2 — Explorer integration

Add a context-menu entry on `.pdf` files.

**The wording is decided:** `Potpiši koristeći Liro Bridge`, or, where space is short, `Potpiši - Liro Bridge`. Not "Potpiši Liro Bridge-om".

- Registered under `HKCU\Software\Classes\SystemFileAssociations\.pdf\shell\` — per user, no administrator rights, consistent with the installer decision in SPEC §15.
- Multi-select must work. Windows invokes the verb once per file for a classic `shell` entry, so the agent must coalesce invocations arriving within a short window into a single batch rather than opening one window per file. Pick a coalescing window, justify the number, and test it with twenty files selected at once.
- The menu entry carries the Liro icon.
- Registration is toggleable in Settings, on by default, and removed cleanly when switched off.

## Part 3 — The job queue

Signing many documents is the case this product exists for. One hundred documents on one PIN was measured at roughly 46 seconds.

- One list, signed in order, one card session, one PIN.
- Per-file state: waiting, signing, done, failed, skipped.
- Overall progress with an ETA, computed from the measured first signature — never from a constant. SPEC §12.9: the first signature costs about 4 seconds of card initialisation and the rest about 0.41 seconds each, but those are observations, not values for the code.
- **"Preparing card…"**, indeterminate, for the first signature. Four seconds of a still progress bar reads as a freeze.
- If the PIN policy is detected as per-signature (F2), say so in the progress message.
- **Skip and continue** on a failed document, per SPEC §12.10 — the alternative is asking for the PIN again for everything after it.
- Abort only on `CARD_NOT_PRESENT` and `PIN_LOCKED`, where continuing is pointless.
- A **Stop** button that finishes the document in flight and stops cleanly. Never leave a half-written file.

## Part 4 — Output

- Default `document.pdf` → `document-signed.pdf`, suffix configurable, already in Settings.
- Choose an output folder, defaulting to the input's own folder.
- The existing-file choice from F5 — Save as, Overwrite, Cancel — applies here, and the answer applies to the rest of the batch. Every output path is settled **before** the card session opens, so cancelling never costs a PIN entry.
- **The original is never silently overwritten.** SPEC §18.10.

## Part 5 — The batch report

When the run ends, show what happened: how many succeeded, how many failed and why, where the files are, and the achieved signature level. A button to open the output folder.

Failures are listed by file name with the reason in words, not a code — SPEC §7 and F5's rule that no error code reaches the interface.

Offer to export the report. The audit log already records the batch; this is for the person, not for the record.

## Part 6 — The stamp gets its own window

The owner's request after using F5: the stamp controls do not belong squeezed onto the consent screen.

A separate window, opened from the consent screen and from Settings:

- Visible stamp on or off
- Corner: bottom-right (default), bottom-left, top-right, top-left
- Target page: first, last, or a number
- The reference line
- Whether to show the identity document number — off by default, SPEC §13.5

The choice persists, and the consent screen shows the current setting in one line with a link to change it. The four corners only; a visual placement picker is a separate phase.

**Margins are enforced.** The original Bridge did not let the stamp sit flush against the page edge, and neither does this one: 24 pt from every edge. When explicit coordinates are supplied, clamp them into the page box less the margin rather than rejecting them — a stamp nudged inside is better than a refusal, and a stamp hanging off the page is not acceptable output.

## Part 7 — Things people do

This is a requirement, not a suggestion. Every case below gets a test, and the standard for each is **a clear message and a clean state** — never a crash, never a silent skip, and never a half-written file left on disk.

The two categories need different answers, and both matter.

**Bad input** — recognise it, name it, skip it, carry on:

- File locked by another program, open in Acrobat
- Read-only file
- Zero bytes
- Not a PDF despite the extension
- Encrypted PDF — `CodePDFEncrypted`, already handled by the parser
- Already signed — must work, this is the normal case
- The same file listed twice
- Path longer than 260 characters
- Name containing Cyrillic, spaces, emoji
- A folder dropped where a file was expected
- Two hundred files at once
- One corrupt file among a hundred good ones

**Bad timing** — leave clean state behind:

- Card removed at document fifty
- PIN cancelled
- Window closed mid-batch
- Machine locked mid-batch — the session's 90-second idle timeout fires, and the batch must end cleanly rather than hang
- Network drive disappears mid-batch
- Disk fills at document seventy
- Output file opened in Acrobat while being written — on Windows the write fails and the original must survive untouched

And one that is specific to this product: **the user picks the wrong certificate.** On a bookkeeper's machine holding several clients' certificates this is a matter of time, not an accident. The consent screen already says whose certificate is being used, in the largest text on screen, and there is no "remember last used". Keep both properties; add a test that the selection does not persist between runs.

## Rules

- Parts 0 through 7, nothing else. No HTTP, no SDK, no installer.
- **No synthetic mouse or keyboard input, ever** — D-094. Screenshots; ask the owner to click when a screenshot genuinely requires it.
- **Never kill processes by image name.** Match on the command line, kill by exact PID, only processes this project started.
- **Verify by running the built binary and looking at the windows**, not only by running tests. Every visible defect in F5 passed its tests while being broken on screen.
- **Scope every assertion over produced output to the bytes or state newly written**, never the whole artefact — the trap recorded in D-072 and D-074.
- Rebuild before reporting anything claimed as observed. A stale binary has cost this project a round already.
- Every colour from a token; `checkcss` stays green. Every new string in all three catalogues; help and usage text stays English.
- Every existing test must pass. No `//nolint`.

Run the full check suite with `-count=1`, on Windows, with and without the `softtoken` tag.

**Report progress after Part 0**, before starting Part 1, stating what the Trusted List discrepancy turned out to be and confirming CI is green.

**When finished, report:** what you built, which checklist items are ticked and which are not, what decisions you recorded, how each case in Part 7 behaves and how you tested it, and anything in SPEC or F6 that was unclear.

The manual acceptance items need real hardware and human eyes — report them as pending.
