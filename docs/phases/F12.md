# Phase F12 — Linux

**Prerequisite reading:** `docs/SPEC.md` in full, `docs/decisions.md` in full, `docs/f11-report.md`, and F11's own phase document. D-268 through D-284 are the PKCS#11 measurements this phase builds on and several of them are about to be re-measured on a platform where the answer differs.

**Prerequisite phase:** F11 closed. A PKCS#11 backend signs with a real Pošta card on Windows, with `CGO_ENABLED=0`, and is deliberately not wired into the agent.

**Goal of this phase:** Liro Bridge runs on Linux. A person installs a package, approves a signature in a window, and gets a signed PDF back.

**Explicitly not in this phase:** no macOS, no new capability, no protocol change, no change to the PAdES engine. Windows behaviour is untouched except where a shared file has to learn a second platform.

---

## 0. Why this phase is unlike the eleven before it

Every phase until now added something to a program that already ran. This one makes the same program run somewhere it never has, and the assumptions it breaks are not in the code — they are in the specification.

Three of them, stated at the top because each is a decision rather than a task:

- **`cgo` becomes unavoidable**, and SPEC §1's single binary with no runtime dependencies stops being literally true.
- **The consent window cannot put itself in front of anything.** Wayland has no protocol for it. SPEC §6.5's arrangement survives, but the mechanism it assumed does not.
- **The system tray does not exist** on a stock GNOME desktop, which is what Fedora ships.

None of these is a Linux inconvenience to work around. Each is the platform saying that something this program took for granted was a Windows fact rather than a general one.

### 0.1 What a virtual machine can and cannot prove

Most of this phase can be built without hardware, on a VPS or a VM, using F2's soft token — the same arrangement that let F3 through F6 be built before a card existed.

What a VM cannot show, and what the exit condition therefore needs:

- **A real reader and a real card.** A VPS has no USB. A local VM can pass a reader through; a rented one cannot.
- **The GPU path.** A VM renders in software, so the DMABUF and NVIDIA failures in §3.2 are invisible there. A VM that works proves nothing about a laptop with an NVIDIA card.

Plan the phase around that split from the first day rather than discovering it at the exit condition. Say in the report which findings came from which.

## 1. `cgo`, and the amendment to SPEC §1

F11 established that `CGO_ENABLED=0` survives on Windows, and proved it to a certificate parsed off a real card. **That result does not carry to Linux**, for two independent reasons:

**The webview.** There is no way to show an HTML window on Linux without linking against the system's WebKitGTK, and every Go binding to it is cgo.

**The PKCS#11 struct layout.** F11's hand-marshalled templates work because PKCS#11 structures are packed to one byte on Windows and `CK_ULONG` is four. On Linux the header uses native alignment and `CK_ULONG` is eight — `CK_ATTRIBUTE` is 24 bytes rather than 16. Writing a second hand-rolled layout is possible and is the wrong answer: F11 measured that three of four candidate layouts return `CKR_OK` with a zero length, so a wrong layout does not announce itself. Use cgo with the platform's own `pkcs11.h` and let the compiler compute the offsets.

So SPEC §1 needs an amendment, and it is the owner's before any code is written. Draft it and show it. Two things it must say rather than imply:

- **What changes.** On Linux the binary links against the system's WebKitGTK and its GTK stack, and the package declares them. That is a dependency in the ordinary packaging sense — it is not a bundled runtime and it is not a second program to install by hand.
- **What does not change.** Windows keeps `CGO_ENABLED=0` and keeps the single binary. The amendment is conditioned on the platform, the way §6.5.1 is conditioned on the module.

And note the consequence F11's handover already flagged: `-race` needs cgo, and `cmd/liro-bridge` has never been race-checked anywhere. With a C toolchain present on Linux, that becomes possible for the first time. Not this phase's job; say so in the entry so the next person finds it.

## 2. The PKCS#11 worker process

D-275 deferred an out-of-process remedy for a module that kills the host, and gated the agent's use of the backend behind it. Independently, the Linux advice arrives at the same arrangement for different reasons: a vendor module `dlopen`ed into a process that also holds GTK and WebKit can collide on OpenSSL and glib symbols, can install signal handlers that crash a Go runtime, and can hold per-thread state that goroutine migration breaks.

**So build it here, and build it for both platforms.** This is the phase where the deferred debt is paid, because Linux requires it anyway.

Requirements:

- **The same binary with a subcommand**, not a second artefact. `pkcs11reach_test.go` exists to stop the agent importing the backend directly; deleting that test is part of doing this, and the entry must say so.
- **Load with `RTLD_LOCAL`, never `RTLD_GLOBAL`.** A vendor module's OpenSSL must not be visible to anything else in the process.
- **One goroutine owns every PKCS#11 call**, pinned with `runtime.LockOSThread`. Everything else reaches it through a channel.
- **`C_Initialize` with `CKF_OS_LOCKING_OK`.** `C_Finalize` only on shutdown or a deliberate reset.
- **A worker that dies is a `Failure` in a list**, which is what F11 §3 already asks discovery to produce. The parent survives, says which module, and carries on with the ones that did not.
- **The subcommand must not become a way in.** D-222 and D-228 spent two phases keeping hidden modes out of a release binary. This one is reachable, so it needs the same scrutiny: it signs nothing, it holds no consent, and it cannot be driven into signing by anything but the parent that spawned it.

Then, and only then, F11 §4 — which source signs, one certificate to one row across two backends, and what the audit log records.

## 3. Windows

### 3.1 The stack

GTK4 with WebKitGTK 6.0, which sets the floor at **Ubuntu 24.04, Debian 13, Fedora 40**. The alternative — GTK3 with `webkit2gtk-4.1` — reaches Ubuntu 22.04 and Debian 12, and is being removed from the Go bindings that offer it.

Take GTK4 and say so in the entry with the dates: Ubuntu 22.04's standard support ends in April 2027, and this program's first Linux release will not precede it by much.

Establish which Go binding rather than assuming one. The requirement is several windows and a tray, which narrows it; check what each costs in dependencies and in how much of this program's existing window code can be kept.

### 3.2 The two failures that will happen on somebody's machine

**Blank windows.** WebKitGTK's DMABUF renderer produces empty windows on several Wayland and driver combinations — KDE's KWin, NVIDIA, some Mesa stacks. `WEBKIT_DISABLE_DMABUF_RENDERER=1` fixes it and costs software rendering. For windows that draw a form and a list, that cost is nothing; set it, but respect the value if the user has already set one, including to `0`.

**NVIDIA on Wayland won't start at all** without `__NV_DISABLE_EXPLICIT_SYNC=1`. Different symptom, different variable, same class.

Both must be set before GTK initialises. Neither can be measured in a VM, so they go in on the advice and are verified when hardware exists.

**The sandbox.** WebKitGTK 6.0 always sandboxes its web process and needs `bubblewrap`. On Ubuntu 23.10 and later, AppArmor restricts user namespaces and `bwrap` can fail outright. Establish whether it works on Ubuntu 24.04 with the distribution's own package. `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1` exists and is defensible only because every page this program loads is local and embedded — but do not reach for it before measuring whether it is needed.

## 4. Consent on Wayland

SPEC §6.5 says a person approves every signature in the agent's own window. That survives. What does not survive is the assumption that the window can make itself seen.

**There is no always-on-top on Wayland.** No protocol lets a client raise itself; the compositor decides. So:

- **A new window for every request**, not a hidden one shown again. GNOME's focus-stealing prevention gives a new window focus in the default mode and gives an existing one only a "ready" notification.
- **A desktop notification alongside**, because clicking it is a legitimate activation and carries the token that a background process receiving an HTTP request does not have.
- **The caller is told to look**, and the caller's own timeout still governs. `PROTOCOL.md`'s consent timeout does not change; what changes is that nothing may assume the person saw the window the instant it opened.
- **Nothing in the security argument may depend on the window being in front.** If any part of the consent design rests on that today, find it and say so.

### 4.1 The X11 fallback is worse than the problem

Running under XWayland restores always-on-top. It also restores something else: **under X11 any local client can send synthetic input to any window**, so `xdotool` can click Approve. Under Wayland it cannot.

This program has refused synthetic input in its own tests since D-094, on the grounds that a test which clicks its own button proves nothing. The same reasoning applies with far more force to an attacker. **Native Wayland is the safer target and the X11 fallback is not to be used**, and the entry should say that in those terms — it is the rare case where the harder path is also the more secure one.

## 5. The PIN dialog

SPEC §10 says one window in this program is native rather than HTML, and §6.5.1 clause 2 says why: the PIN must exist only for the length of one `C_Login` and be overwritten, and a page rendered in a browser view is not this program's memory. WebKitGTK runs the page in a separate process exactly as WebView2 does, so the reasoning carries unchanged.

The Linux advice recommends putting the PIN field in the HTML window, on UX and anti-spoofing grounds. **Those are good reasons and they do not override clause 2** — but the tension is real and the entry should record it rather than pretend the question did not arise.

So: a native dialog, and the decision is which.

- **A GTK dialog this program draws**, matching what Windows does.
- **`pinentry`**, GnuPG's, which looks native on each desktop and is the standard answer — but is a separate process, a package dependency, and a thing an attacker could imitate.

Establish both and recommend one before building. Whichever it is, clause 2's requirements are unchanged: enforced `ulMinPinLen` and `ulMaxPinLen` read from the token, no retry ever, overwritten immediately, in no struct field or closure, and the dialog says it is Liro Bridge asking.

The AST guard in `internal/keysource/pkcs11` must cover whatever new package holds this. It is the reason the Windows seam is a callback filling a caller-owned buffer rather than a function returning a `[]byte`, and that shape should survive the port.

## 6. The tray, which is not there

A stock GNOME desktop has no system tray. Ubuntu ships an AppIndicator extension; Fedora does not. So on one of the two reference distributions, the tray icon this program has had since F5 simply does not appear.

Decide, and record:

- Whether the agent runs with no visible presence at all on such a desktop, and how a person then reaches Settings, the certificate list and the audit log.
- Whether a `.desktop` entry launching the window is the answer, with single-instance handing the request to a running agent.
- What "Quit" means when there is nothing to right-click.

This is a product decision, not a packaging detail. Do not solve it by requiring an extension.

## 7. Secrets, and the audit log's home

**Secret Service** where it exists — GNOME Keyring, KDE's `ksecretd`. It does not exist on minimal desktops, and on those the D-Bus call simply fails.

The fallback is a file with `0600` permissions under `$XDG_CONFIG_HOME`, and the reasoning for why that is acceptable belongs in the entry: an unlocked keyring does not protect against malware running as the same user either. Both protect against other users of the machine.

**The PIN is never stored, in either.** That is not a Linux question; it is clause 4 of §6.5.1.

And the paths: `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME`, `$XDG_STATE_HOME`, `$XDG_RUNTIME_DIR`, none of them beside the binary. `platform.ConfigDir` already takes an OS argument; this is what it was for.

The audit chain's cross-process guard (D-229, D-234) carries the exclusion on `LockFileEx` on Windows and `flock` elsewhere. **This document said the `flock` path was "written but never exercised" and that was wrong** — `internal/platform/dirlock_other.go` uses `syscall.Flock`, `dirlock_test.go` carries no OS suffix, and CI's Ubuntu job has run `go test ./... -race` over it on every push since F9b; D-229 records both suites being run on a real Linux kernel rather than only cross-compiled. So this is not where that path first runs. What is genuinely new here is the *directory* it guards moving to `$XDG_STATE_HOME`, and confirming the lock still excludes across two processes once it has.

## 8. Packaging

**`.deb` and `.rpm` from one nFPM configuration.** Flatpak and Snap are out, and for a reason worth recording rather than asserting: a sandboxed package cannot load a vendor PKCS#11 module that the user installed system-wide, which is the whole point of F11.

- **Declare the dependencies**: WebKitGTK and its GTK stack, `pcscd`, `libpcsclite1`, `libccid` — and the Fedora names differ from the Debian ones, so the two dependency lists are written separately.
- **Build in a container with the oldest supported glibc.** A cgo binary built on the newest Fedora will not start on Ubuntu 24.04. The build container is not a test distribution.
- **Autostart** is an XDG `.desktop` file in `~/.config/autostart`, written and removed by the program when the setting changes. Not a systemd user unit: a GUI process started before the graphical session exists is a defect with no good symptom.
- **The desktop entry** carries the icon, and on GNOME a file in `~/Desktop` must be marked trusted or it renders as text. Windows' equivalent was settled in D-283; this is its Linux half.
- **`MimeType=application/pdf`** gives an "Open with" entry in every file manager. There is no universal context menu on Linux — Nautilus has scripts, Dolphin has service menus — so do not try to reproduce the Explorer verb.
- **Updates**: the signed manifest and the daily check from F10 work unchanged, but a package manager is the expected route on Linux. Decide whether the in-app updater offers to download at all here, or whether it only says a version exists.

## 9. `pcsclite`

Not present by default, and nothing installs it when a reader is plugged in. Declared as a package dependency, with the names above.

Two things worth building in because they will otherwise arrive as support questions: `pcscd` is socket-activated and has historically been left disabled after install, and some readers need a driver outside the generic CCID one.

Whether this program talks to PC/SC directly is a separate question and the answer is probably not — the PKCS#11 module does it. `C_GetSlotList` with `tokenPresent=TRUE`, polled, is enough to notice a card; `C_WaitForSlotEvent` is often unimplemented.

---

## 10. Module discovery

F11's Windows discovery reads known paths and verifies each candidate exports `C_GetFunctionList` — a test that earned itself against a wrapper with "pkcs11" in its name. The same test applies here.

What differs: multiarch paths (`/usr/lib`, `/usr/lib64`, `/usr/lib/x86_64-linux-gnu`), the **p11-kit registry** at `/usr/share/p11-kit/modules/*.module`, which Windows has no equivalent of, and vendor modules that do not register themselves there.

And a failure mode Windows does not have: an older vendor module can want symbols from an OpenSSL the distribution no longer ships, and `dlopen` fails with an undefined symbol rather than anything meaningful. That is a `Failure` with a readable reason, not a crash.

A configured path remains the escape hatch, and a protocol-supplied path remains refused.

## 11. Testing

**Ubuntu 24.04 LTS and Fedora Workstation 44.** Together they cover the widest span for two machines: AppArmor against SELinux, GNOME 46 with Ubuntu's extensions against stock GNOME 50, Wayland with X11 still available against Wayland only, older glibc against newer, deb against rpm.

A KDE live image for half an hour is worth it if a third is possible: `ksecretd`, KWin's focus behaviour, and the tray.

**A VM is not hardware**, per §0.1. Say which findings came from which.

## Rules

This phase only. No macOS, no new capability, no protocol change, no change to the signing engine.

**Answer §1 before building on it.** The amendment to SPEC §1 is the owner's and it stops the phase until it is made.

Measure rather than reason. Write your predictions down before you measure — every session of F11 that did this caught something, and the ones whose predictions failed were the most useful.

**Verify signatures with the independent verifier of SPEC §16.4**, never by observing that a call returned bytes. On a new struct layout that warning is not historical: three of four candidates returned `CKR_OK` and lied, on Windows, measured.

No synthetic input (D-094) — and on this platform that rule has a second edge, §4.1. Exact PID only. Observe the property rather than time the machine (D-201). No `//nolint`. Leave every machine as you found it, proven against your own snapshot.

Record a decision for each choice above that says *decide and record*.

**Report:** what `CGO_ENABLED` became and on which platform; what the struct layout measured out at; whether the sandbox worked on a stock Ubuntu 24.04; what the consent window does when it cannot raise itself, demonstrated rather than described; which PIN dialog and why; what a stock GNOME desktop shows when the agent is running; and which findings came from a VM rather than from hardware.
