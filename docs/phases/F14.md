# Phase F14 — The cloud channel

**Prerequisite reading:** `docs/SPEC.md` §1, §2, §6.5, §6.6, §6.7 and §7; `docs/PROTOCOL.md` in full; D-179 (the protocol is unreachable from a browser), D-434 (the owner's definition of this channel), D-461 (this document's decisions).

**Goal of this phase:** a web application that runs on a server somewhere else — a cloud ERP, a document portal — can ask the person at a machine to sign, and get the signature back, **with the key on the card in front of that person and a person pressing Approve**, exactly as a program on the same machine can today.

**Explicitly not in this phase:** any change to the loopback protocol other than version negotiation (§8); a key anywhere but the card; signing with nobody present; a background connection to any server; push; polling; a second signer, a routing step or any other workflow (SPEC §2).

---

## 0. What this is, and the thing it is not

**SPEC §2 excludes cloud signing, permanently, and nothing in this phase touches that exclusion.** What SPEC §2 excludes is a key that lives on a server and signs with nobody present — a "remote signing" service, a hardware security module in a data centre, a signature made because a server decided to make one. That stays out of scope for good: it is the opposite of the design centre (§1: *the private key never leaves the card, the document never leaves the machine, and no signature is ever created without a human clicking a button*), and no amount of convenience changes it.

**The cloud channel is a different thing.** It changes one thing only: **how a request reaches the person.** Today a request can come from a program on the same machine, over loopback. A cloud ERP cannot reach that: the browser cannot call the loopback API (D-179, by construction), and the server cannot reach the person's loopback at all. So:

1. The server makes a job and hands the person, in their browser, a link: `liro-bridge://sign?job=https://erp.example.com/liro/jobs/…`.
2. The person clicks it. The operating system opens the local agent with the link.
3. The agent fetches the job from that server over HTTPS.
4. The agent shows the same consent window it shows for every other request. The person approves, enters the PIN; the card signs.
5. The agent sends the signature or the signed documents back to that server over HTTPS.

The key never leaves the card. The person approves every batch, in the same window, with the same timeout and the same audit entry. **The document leaves the machine only in the sense that it was never on the machine to begin with**: it came from the server, and the signed result goes back to the server it came from, at the person's approval — which is what the person asked for when they clicked a link on that server's page. §1's "the document never leaves the machine" is about this program never sending a person's own documents anywhere; it sends a server's own document back to that server and nowhere else.

SPEC §2's row is amended to say exactly this (§10 below).

## 1. The link

`liro-bridge://sign?job=<https URL>`

- The scheme is `liro-bridge`, registered per user by the agent itself the way the Explorer verb is (Windows: `HKCU\Software\Classes\liro-bridge`, with `URL Protocol`; Linux: the package's `.desktop` file declares `x-scheme-handler/liro-bridge`; macOS: `CFBundleURLTypes`, F13).
- The command it runs is `liro-bridge open-link <url>`. That process does what every other launch does: if an agent is running, it hands the link to it (the existing single-instance handover, `RequestOpen`) and exits; if none is, it becomes the agent.
- **One action, `sign`.** A link is parsed strictly: the scheme, the host part `sign`, exactly one query parameter `job`, nothing else; anything else is refused and logged, and the person is told the link could not be used.
- **The job URL must be `https`**, with a host, no user information, no fragment, at most 2048 bytes. No `http`, no other scheme, no exception for `localhost` — a server on the same machine has the loopback protocol.

**A link is not trusted for anything.** Any web page, any e-mail and any program on the machine can produce one. Everything below follows from that: the link only says *where to look*, and the person decides.

## 2. Which servers may send requests: the person's list

The first time a link names a server (its origin: scheme, host and port), the agent does not fetch anything. It shows a window: **“erp.example.com wants to send you documents to sign. Allow?”** — the origin as the agent parsed it from the link, never a name the server supplied. Only on **Allow** is the origin added to the person's list, and only then is the job fetched.

- The list is per user, beside the pairings (`cloud-origins.json`, 0600), and Settings shows it with a Remove beside each origin (the pairings list's own pattern).
- **The consent window names the origin**, as it names the paired application for a loopback request (SPEC §6.6): the name in the window is the host the agent connected to over TLS. A server cannot present itself as anyone else, because the only name the window shows is the one the certificate chain was checked against.
- Allowing an origin authorises nothing on its own. **Every batch still goes through the consent window**, with its document names and its batch fingerprint, and still needs the PIN.

**Decided (D-461): no device secret for a server, in this phase.** The loopback protocol pairs with a secret because the agent must know which program on the machine is asking. Here the agent connects *out*, to a server it identifies by TLS, using a URL the server made; what the server needs to know — that the result came from the person it asked — is proved by the signature itself, made by the person's own certificate, which the server must validate anyway (§6). A secret would add a second credential to store and rotate and would prove nothing the signature does not. If a later need appears (a server that wants to know *which machine* answered), it is a new version of this protocol, negotiated (§8).

## 3. The cloud protocol, version 1

Two requests, both from the agent to the server, both HTTPS.

### 3.1 Fetching the job

```
GET <job URL from the link>
Accept: application/json
User-Agent: LiroBridge/<agentVersion> liro-cloud/1
```

`200` with `Content-Type: application/json`:

```json
{
  "protocol": "liro-cloud/1",
  "kind": "documents",
  "documents": [ { "name": "Ugovor 114.pdf", "content": "<base64>" } ],
  "level": "b-t",
  "resultUrl": "https://erp.example.com/liro/jobs/7f3…/result"
}
```

- `protocol` is required. **An agent refuses a job whose protocol it does not speak** — a different major version — and says which it speaks (§8).
- `kind` is `"documents"` (the server sends PDFs and gets signed PDFs back — `POST /v2/sign/pdf`'s body) or `"digests"` (the server builds CMS and gets raw signatures — `POST /v2/sign`'s body, with `certificateThumbprint`, `digestAlgorithm`, `digests`, `labels`). **The fields, their limits and their validation are the loopback protocol's own** (`PROTOCOL.md` §5), parsed by the same code: a document this agent would refuse over loopback it refuses here, for the same reason, in the same words.
- `resultUrl` is required and **must have the same origin as the job URL**. The agent sends nothing to any other origin.
- Limits: the response body at most the loopback limit for the same kind; 30 s to connect and answer; no redirects (a `3xx` is a failure — a redirect to another origin is exactly what the same-origin rule forbids, and a redirect within one is not needed); no cookies, no stored credentials, no proxy authentication from the agent's side; certificates checked against the system's roots, with no option to turn that off.

A `404` or `410` is a job that is gone ("the request has expired or was already answered"); anything else non-`200` is a server that could not be reached or would not answer.

### 3.2 Returning the result

```
POST <resultUrl>
Content-Type: application/json
```

```json
{
  "protocol": "liro-cloud/1",
  "batchFingerprint": "<hex, as the consent window showed it>",
  "documents": [ { "name": "Ugovor 114.pdf", "content": "<base64>", "achievedLevel": "B-T" } ],
  "failures": [],
  "counts": { "total": 1, "succeeded": 1, "failed": 0 }
}
```

— the loopback result body (`GET /v2/jobs/{id}/result`) with the protocol and the fingerprint added. For `"digests"`, `signatures` in place of `documents`.

When the person refuses, the window times out, or nothing can be signed, the agent still posts — `{"protocol":"liro-cloud/1","code":"CONSENT_DENIED"}`, with SPEC §7's code — so the server's page can say what happened rather than wait. The server answers `2xx`; the agent retries a failed post twice, then tells the person the signature was made and could not be delivered, and keeps nothing (the signed documents are not written to disk on the agent's side: they were the server's).

## 4. What the agent records

The audit entry is the loopback request's (SPEC §6.7), with `origin` set to the job URL's origin and the job URL's path recorded **without its query string** — a capability token in a URL is a credential and does not go into a log or an audit chain.

## 5. Threats, and what answers each

| threat | answer |
|---|---|
| A page the person happens to visit produces a link to an attacker's server | The first link from an origin asks the person, naming the origin; the consent window names it again; the person approves each batch with its document names. The same defence as the loopback pairing, with the origin in place of the application name |
| A link to a server the person allowed, carrying an attacker's job URL path | The job URL must be on the allowed origin; whatever it fetches is still shown in the consent window before anything is signed |
| A server redirecting the agent elsewhere (SSRF) | No redirects; `https` only; one origin; size and time limits |
| The result sent somewhere other than where the job came from | `resultUrl` must have the job's origin |
| A capability token leaking through logs | The query string is never logged or audited |
| A flood of links | One consent window at a time — the loopback slot (`protocolSigner`) is the same slot |
| TLS interception by a proxy the person did not choose | System roots only; no option to skip verification |
| A server presenting itself as another | The name shown is the TLS-checked host, never a server-supplied string |

## 6. What a server must do

Serve the two URLs; make the job URL unguessable and single-use; expire it; **validate what comes back** — the signature, the certificate, the batch fingerprint against what it sent. Nothing the agent does replaces that: the agent proves to the person what they are signing, and the signature proves to the server who signed.

## 7. What changes in the agent

- `open-link` subcommand; the URL scheme registered at start and removed by the uninstaller, as the Explorer verb is (F10 §3.1, D40's caveat applies equally).
- `internal/cloud`: the link parser, the job client and the result client — pure Go, HTTP with the limits above, testable against `httptest` servers.
- The allowed-origins store and its window.
- The job enters the same `api.Signer` the loopback protocol uses, so the consent window, the slot, the timeout, the PIN dialog and the audit entry are the loopback ones by construction.

## 8. Protocol version negotiation (the loopback protocol)

The SDK used to refuse an agent whose `protocolVersion` was anything but its own (`bridge.ts`), which means **the first agent that ever speaks a version 3 would be refused by every SDK written for version 2**, even if it still speaks 2. The negotiation:

- `GET /v2/health` (and `bridge.json`) gain `protocolVersions`: every version this agent speaks, ascending. `protocolVersion` stays, meaning the newest, for clients that predate this.
- A client picks the highest version it shares with the agent and sends `X-Liro-Protocol: <n>` on every request. An agent that does not speak `n` answers `426` with `PROTOCOL_UNSUPPORTED` and `details.protocolVersions`. A request without the header is version 2, which is what every client before this sends.
- An SDK refuses an agent only when the two share no version, and says which versions each speaks.
- The cloud protocol carries its own version in its body (`"protocol": "liro-cloud/1"`), negotiated the same way in its own direction: the agent refuses a job in a major version it does not speak and posts back the versions it does.

## 9. Not in this phase

A server-side secret (§2); a way for a server to reach an agent without the person clicking something; a job list; background fetching; any state kept between jobs except the allowed origins.

## 10. SPEC amendments

- §2, the first row: *Cloud / remote signing* becomes *Signing in the cloud: a key held anywhere but the person's own card, or a signature made with nobody present* — with the reason unchanged, and a sentence that the cloud channel (this document) is a way for a request to reach the person, not a way to sign without them.
- §4.3's list of entry points gains the cloud channel, through the same consent screen, session and audit log.

## 11. Exit checklist

- [ ] The link parser, the job client and the result client tested against `httptest` servers, every refusal with its own test.
- [ ] Version negotiation in the agent and the TypeScript SDK, with an agent that speaks only a version the SDK does not refused for the right reason.
- [ ] `open-link` hands a link to a running agent on all three platforms.
- [ ] The scheme registered and unregistered on Windows, measured in the registry.
- [ ] **A person clicks a link in a browser, the agent opens, the person allows the origin, approves, enters the PIN, and the server receives a signature that verifies.** Needs a person, a card and a server — the last can be the test server shipped for it.
