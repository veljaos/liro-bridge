# Phase F2 — Signing sessions

**Prerequisite reading:** `docs/SPEC.md` in full, then `docs/decisions.md` in full.

**Prerequisite phase:** F1 complete, checklist green.

**Goal of this phase:** the agent can open a signing session against a real smart card, produce raw RSA signatures over pre-computed digests, sign a batch of many digests on a single PIN entry, and measure its own timing. The whole pipeline must be testable with no hardware at all.

**Explicitly not in this phase:** no PDF, no CMS, no timestamps, no HTTP, no UI. This phase signs *digests*. It has no idea what a document is.

**Exit condition:** `liro-bridge sign-digest` produces a signature over a given hash that verifies with OpenSSL against the certificate's public key, and the same command works against the soft token with no card present.

---

## 1. Why this phase is separated from PAdES

The PDF engine in F3 is the riskiest part of the project. It must be developed against a signing backend that already works, otherwise every failure has two possible causes.

By the end of F2 you will be able to sign anything, with or without hardware, and verify it externally. F3 then only has to get the document format right.

## 2. The Windows CNG session

**Package:** `internal/keysource/windowscng`, file `session_windows.go`.

### 2.1 Acquiring the key handle

From the certificate context obtained in F1:

```
CryptAcquireCertificatePrivateKey(
    pCert,
    CRYPT_ACQUIRE_ONLY_NCRYPT_KEY_FLAG,   // 0x00040000
    NULL,
    &hKey,
    &dwKeySpec,
    &fCallerFree)
```

- `CRYPT_ACQUIRE_ONLY_NCRYPT_KEY_FLAG` forces the modern CNG path. Without it you may receive a legacy CSP handle, and the signing call is then a completely different API. F1 established that all three supported issuers surface through `Microsoft Smart Card Key Storage Provider`, so CNG is always available.
- `dwKeySpec` must come back as `CERT_NCRYPT_KEY_SPEC` (`0xFFFFFFFF`). Anything else means you got a legacy handle; treat it as `errs.CodeSignFailed` and log the value.
- **`fCallerFree` decides ownership.** If it is false, the handle is cached by Windows and **must not** be freed — freeing it corrupts the cache for every other process. Store the flag in the session and honour it in `Close`.

### 2.2 Signing

```
NCryptSignHash(
    hKey,
    &BCRYPT_PKCS1_PADDING_INFO{ pszAlgId: BCRYPT_SHA256_ALGORITHM },
    pbHash, cbHash,
    NULL, 0, &cbResult,          // first call: ask for the size
    BCRYPT_PAD_PKCS1)            // 0x00000002
```

Then call again with a buffer of `cbResult`.

`BCRYPT_SHA256_ALGORITHM` is the wide string `"SHA256"`. It must be a null-terminated UTF-16 pointer that stays alive for the duration of the call — a common Go mistake is letting the Go string be collected. Use `windows.UTF16PtrFromString` and keep the result in a variable, not inline in the struct literal.

The digest length must match the algorithm: 32 bytes for SHA-256. **Validate it before calling.** A wrong length produces `NTE_INVALID_PARAMETER` from deep inside the driver with no useful message.

### 2.3 The PIN is never ours

**Decision to implement and record:** the agent does not collect, transport, store or see the PIN. The smart card KSP shows the operating system's own PIN dialog on the first signing operation.

Consequences:

- Do **not** set `NCRYPT_PIN_PROPERTY`. Do not add a PIN field to any struct or API.
- Do **not** pass `NCRYPT_SILENT_FLAG`. Silent mode fails instead of prompting, which is the opposite of what a desktop agent wants.
- **Do** set `NCRYPT_WINDOW_HANDLE_PROPERTY` on the key handle to the agent's own window handle before the first signature, so the PIN dialog is parented correctly and appears in front. Without it the dialog can open behind the agent window and the application looks frozen. In F2 there is no window yet, so pass zero and leave a comment pointing at F5.

This is not merely convenient. A PIN that never enters our process cannot leak from our logs, our crash dumps or our memory.

### 2.4 Error mapping

| Windows status | Error code |
|---|---|
| `SCARD_W_CANCELLED_BY_USER` (`0x8010006E`) | `CodeConsentDenied` |
| `SCARD_W_WRONG_CHV` (`0x8010006B`) | `CodePINIncorrect` |
| `SCARD_W_CHV_BLOCKED` (`0x8010006C`) | `CodePINLocked` |
| `SCARD_W_REMOVED_CARD` (`0x80100069`) | `CodeCardNotPresent` |
| `NTE_BAD_KEYSET` (`0x80090016`) | `CodeCertNotFound` |
| `NTE_NO_KEY` (`0x8009000D`) | `CodeCertNotUsable` |
| anything else | `CodeSignFailed`, with the hex status in `Details` |

Never retry a PIN failure automatically. The card has a retry counter, and an automatic retry burns it. Three wrong PINs typically block the card and require a PUK.

## 3. The soft token

**Package:** `internal/keysource/softtoken`

### 3.1 Purpose and hard constraints

This exists so the entire pipeline — F2 through F6 — can be developed and tested without hardware. It is the reason F3 can proceed while your card is in a drawer.

Two constraints from SPEC §16.6, both mandatory:

1. **Build-tagged out of release builds.** Every file in the package begins with `//go:build softtoken`. The release build does not pass that tag, so the package is not compiled at all. Add a CI step that builds without the tag and greps the binary to confirm the package symbols are absent.
2. **Every signature it produces is visibly marked as a test signature.** The `Certificate` it returns carries `IsTestKey: true`, which propagates into `classify.Info` and into every audit entry and UI surface downstream.

### 3.2 Implementation

Backed by a PKCS#12 file. Configuration via environment variables, never via the config file — this must not be enable-able by a user who edits JSON:

```
LIRO_SOFTTOKEN_P12=/path/to/test.p12
LIRO_SOFTTOKEN_PASSWORD=...
```

Implements the same `keysource.Source` and `keysource.Session` interfaces. `Open` loads the key; `SignDigest` performs `rsa.SignPKCS1v15`. There is no PIN.

### 3.3 Test key generation

Add `scripts/gentestkeys` producing a self-signed RSA-2048 certificate and its PKCS#12, written to a gitignored directory. Do **not** commit a private key, even a test one — a committed key ends up copied into something real eventually.

The generated certificate must carry `contentCommitment` in its key usage, so that classification treats it as a signing certificate and the whole path is exercised.

## 4. Sessions

**Package:** `internal/signing`

### 4.1 Lifetime — explicit numbers

| Parameter | Value | Reasoning |
|---|---|---|
| Idle timeout | **90 seconds** | Long enough for a user to answer a phone call mid-batch; short enough that a walked-away-from machine does not hold an authenticated card open. |
| Maximum lifetime | **30 minutes** | An absolute ceiling regardless of activity. A batch of 1000 documents at 0.41 s each is under 7 minutes, so this never truncates legitimate work. |
| Approval-to-first-signature window | **120 seconds** | The user has approved; if signing has not begun in two minutes something is wrong. |

On idle timeout, close the session and free the key handle. The next operation requires a new approval and a new PIN.

**These are the numbers, not suggestions.** If you believe one is wrong, implement it as specified and argue in `decisions.md`.

### 4.2 Concurrency

A `Session` is **not** safe for concurrent use — SPEC §8.5. One session is owned by one batch, and the batch signs sequentially.

Sequential is deliberate. Parallel signing against one card does not help: the card is a single serial device, so requests queue in the driver anyway, and concurrent access is a known source of driver-level failures. Record this as a decision so nobody "optimises" it later.

Multiple *sessions* may exist for different certificates. Guard the session registry with a mutex.

## 5. Batches

**Package:** `internal/signing`, file `batch.go`

### 5.1 Shape

```go
// Batch is a set of digests approved together and signed with a single
// PIN entry.
type Batch struct {
    ID          string
    Thumbprint  string
    Items       []BatchItem
    Fingerprint []byte   // SHA-256 over the concatenated digests, in order
}

type BatchItem struct {
    // Digest is a pre-computed hash. Length must match Algorithm.
    Digest    []byte
    Algorithm keysource.DigestAlgorithm

    // Label is a caller-supplied display string. Untrusted input —
    // see SPEC §6.6. Never used as a path, never logged.
    Label string
}

type BatchResult struct {
    Signatures [][]byte      // nil where the item failed
    Failures   []ItemFailure
    Timing     TimingReport
}
```

### 5.2 The fingerprint

`SHA-256` over the concatenation of every digest, in order. It is shown on the consent screen so a technical user can compare what was approved against what the calling application claims it sent (SPEC §6.6).

Compute it **before** approval and re-verify it **after**, immediately before signing. A mismatch means the batch changed between approval and execution: abort with `CodeInternal` and log loudly. This is cheap and closes a real gap.

### 5.3 Failure policy

SPEC §12.10: **skip and continue.** A failed item leaves a nil signature and an entry in `Failures`. The batch proceeds.

Two exceptions where the batch aborts immediately, because continuing is pointless:

- `CodeCardNotPresent` — the card was removed mid-batch
- `CodePINLocked` — the card is blocked

Everything else is skipped and reported.

### 5.4 Timing

```go
type TimingReport struct {
    FirstSignature   time.Duration
    MedianSubsequent time.Duration
    Total            time.Duration
    PINPolicy        PINPolicy
}

type PINPolicy int
const (
    PINPolicyUnknown PINPolicy = iota
    PINPolicyPerBatch          // one PIN unlocks the whole batch
    PINPolicyPerSignature      // ALWAYS_AUTHENTICATE
)
```

Measured on a real e-ID card: **first signature ≈ 4.9 s, every subsequent one ≈ 0.41 s**, varying by under 2 ms across 90 operations. The first-signature cost is card initialisation and cannot be avoided.

### 5.5 Detecting `ALWAYS_AUTHENTICATE` — explicit thresholds

Some cards require a PIN for every signature. SPEC §12.9 requires supporting both policies, detected rather than assumed. There is no reliable property to query, so detect it by timing.

```
After signature 2 completes:
    if duration(sig2) > 2000 ms          → PINPolicyPerSignature
    else                                 → PINPolicyPerBatch

After signature 3, confirm:
    if median(sig2, sig3) > 2000 ms      → PINPolicyPerSignature (final)
    else                                 → PINPolicyPerBatch (final)
```

**Why 2000 ms:** the measured subsequent-signature time is 413 ms. A PIN dialog cannot be shown, filled and dismissed in under two seconds by a human. The threshold sits roughly 5× above normal and far below any plausible human interaction, so neither a slow card nor a fast typist can land in the wrong bucket.

On `PINPolicyPerSignature`: recompute the ETA using the measured per-signature time, and change the progress message to tell the user they will be asked for the PIN repeatedly. Do not abort — it works, it is just slower and more annoying.

A batch of one never determines a policy. Leave it `PINPolicyUnknown`.

### 5.6 ETA — computed, never constant

```
ETA = measured_first + (remaining × measured_median)
```

Before the first signature completes there is no data, so display an indeterminate **"Preparing card…"** state with no numeric estimate.

**Do not hard-code 4900 or 413 anywhere.** Those are observations recorded in this document, not constants in the code. Pošta is migrating to RSA-4096, which will be slower, and a hard-coded estimate becomes a lie.

If the first signature exceeds **30 seconds**, log a warning: something is wrong with the reader or the middleware, even though the operation may still succeed.

## 6. The `sign-digest` command

**Package:** `internal/cli`

```
liro-bridge sign-digest --thumbprint <hex> --digest <hex> [--out signature.bin]
```

- `--digest` is a hex-encoded SHA-256 hash: exactly 64 hex characters. Reject anything else before touching the card.
- Output is raw signature bytes to a file, or base64 to stdout when `--out` is absent.
- `--repeat N` signs the same digest N times in one session, to exercise batching and produce a timing report. Cap N at 1000.

### 6.1 The external verification that closes this phase

This is the exit condition. It must be documented in the README with these exact commands:

```bash
# 1. digest of some file
openssl dgst -sha256 -binary input.txt > digest.bin
xxd -p -c 256 digest.bin

# 2. sign it
liro-bridge sign-digest --thumbprint ABCD... --digest <hex> --out sig.bin

# 3. extract the public key from the certificate
liro-bridge certs --json | jq -r '.[0].pem' > cert.pem
openssl x509 -in cert.pem -pubkey -noout > pub.pem

# 4. verify with a tool that is not ours
openssl dgst -sha256 -verify pub.pem -signature sig.bin input.txt
# expected output:  Verified OK
```

`Verified OK` from OpenSSL means the CNG plumbing, the padding, the digest algorithm identifier and the byte order are all correct. Nothing built in F3 can be trusted until this passes.

Add `--json` output of the PEM certificate to the `certs` command if F1 did not already provide it.

## 7. Tests

### 7.1 Without hardware

Everything below runs in CI with the `softtoken` build tag and no card:

- `SignDigest` over a known digest produces a signature that `rsa.VerifyPKCS1v15` accepts.
- A digest of the wrong length is rejected **before** any backend call.
- A batch of 10 produces 10 signatures in order.
- A batch where item 5 fails produces 9 signatures, one failure entry, and items 6–10 still signed.
- `CodeCardNotPresent` mid-batch aborts; `CodeSignFailed` mid-batch does not.
- Fingerprint mismatch between approval and execution aborts.
- Idle timeout closes the session; a subsequent operation fails with a session error.
- Maximum lifetime closes the session even under continuous activity.

### 7.2 PIN policy detection

Use a fake backend with programmable delays:

| Scenario | Expected |
|---|---|
| sig2 = 400 ms, sig3 = 410 ms | `PINPolicyPerBatch` |
| sig2 = 5000 ms, sig3 = 4800 ms | `PINPolicyPerSignature` |
| sig2 = 1900 ms, sig3 = 1950 ms | `PINPolicyPerBatch` (below threshold) |
| sig2 = 2100 ms, sig3 = 400 ms | `PINPolicyPerBatch` — the median decides, one slow signature does not |
| batch of 1 | `PINPolicyUnknown` |

### 7.3 The build-tag test

A CI step builds **without** the `softtoken` tag and asserts the soft token symbols are absent from the binary. This is the security-check-that-must-fire discipline: write it so that removing the build tag makes CI red.

### 7.4 Manual, with hardware

- `sign-digest` against a real card: OpenSSL reports `Verified OK`.
- `--repeat 20`: one PIN prompt, twenty signatures, timing report shows a slow first and fast rest.
- Remove the card mid-batch: the batch aborts cleanly with `CARD_NOT_PRESENT`, no crash, no orphaned handle.
- Cancel the PIN dialog: `CONSENT_DENIED`, and the retry counter is untouched.

## 8. Decisions to record

Continue the existing numbering.

- The PIN is never collected, transported or stored by the agent; the system dialog is used. Rejected: collecting the PIN in our own UI for a nicer look — it would put a card PIN inside our process for no functional gain.
- `fCallerFree` is honoured; a cached handle is never freed. Include what happens if you get it wrong.
- Batch signing is sequential. Rejected: parallel signing — the card is a serial device and concurrent access is a known driver failure mode.
- The `ALWAYS_AUTHENTICATE` threshold is 2000 ms, with the reasoning from §5.5.
- Session timeouts of 90 s idle and 30 min maximum, with reasoning.
- The soft token is excluded by build tag and its signatures are marked, with the CI check that enforces it.
- Timing constants are measured at runtime, never hard-coded, because of the RSA-4096 migration.
