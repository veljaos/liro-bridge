# Phase F10 — Packaging

**Prerequisite reading:** `docs/SPEC.md` in full, `docs/decisions.md` in full. SPEC §15 is this phase's specification, and §15.1 and §15.2 are unusually prescriptive — follow them rather than improving on them.

**Prerequisite phase:** F9b complete. One `sign`, and it shows the consent window. The audit chain is guarded across processes. Nothing signs without a person.

**Goal of this phase:** a stranger installs it and signs a document.

**Explicitly not in this phase:** no new signing capability, no other platform, no protocol change, no change to the PAdES engine or the consent flow. If this phase changes how a document gets signed, something has gone wrong.

**The phase's own peculiarity, stated at the top because it shapes everything below:** its exit condition cannot be verified by the person who built it. Every phase until now ended in a measurement. This one ends in somebody else's afternoon.

---

## 1. Artefacts

Per SPEC §15:

- **An MSI, per-user, installing with no administrator rights.** This is the primary artefact. An accountant in an office is very often not a local administrator, and an installer that demands elevation is an installer that does not get run.
- **A per-machine option for GPO deployment.** The same MSI with a property, or a second artefact — decide, and record which and why.
- **A plain EXE** for people who prefer one.
- **Published on GitHub Releases.**

Both artefacts install the same binary. There is no "installer edition" of this program.

### 1.1 The version is still `dev`

`version` in `cmd/liro-bridge/main.go` is `"dev"` and no workflow sets it. A release stamps it from the tag through `-ldflags`, and `liro-bridge --version` reports exactly what a person can match against a release page.

Two things read it: the update check of §5 and the protocol's `minimumClientVersion`, whose format F9 settled. A release that ships `dev` is a release that cannot be compared to anything, in either direction.

---

## 2. WebView2

The likeliest single cause of *the stranger installed it and nothing happened*. Establish the facts rather than reasoning about them.

Every window this program has is WebView2. Windows 11 ships the Evergreen Runtime. A Windows 10 machine may not have it, and a machine kept off the internet by policy may not have it either.

- **What the program does today when the runtime is absent.** Measure it, on a machine or image without it, not by mocking the check. A stack trace or a silent exit is the finding, and it is worth having.
- **What the installer does about it.** Detect it, and either bring it in or say something a non-technical person can act on. Establish whether the Evergreen bootstrapper installs per-user without elevation — do not assume either way.
- **What the program says if it is missing at run time anyway,** because the installer's check and the runtime's presence drift.

None of this may become a silent failure. A person who double-clicks and sees nothing has no way forward and no vocabulary to ask for help with.

## 3. Install, upgrade, uninstall

### 3.1 Install

The Explorer verb and `HKCU\...\Run` point at the installed binary, not at a build output. F9b overwrote the repository-root `liro-bridge.exe` that the verb pointed at, because `go build ./...` writes into the working directory. That trap exists only because the registered path is a development path, and this phase is where it stops being one.

State what the person sees on first run, in order, and make it something somebody who has never heard of a signing agent can follow.

### 3.2 Upgrade over a running agent

The agent may be in the tray, may hold a card session, may be mid-batch.

- **An upgrade must not interrupt a signature in progress.** Say what it does instead — waits, refuses, or asks — and demonstrate it with a real batch running, not with a mocked state.
- **The discovery file and the port:** a paired SDK client must not be silently broken by an upgrade. If pairings survive, show it. If they do not, that is a decision and it needs recording rather than discovering.

### 3.3 Uninstall

Removes the binary, the Explorer verb, the autostart entry, the discovery file.

**Does not remove the audit log.** It is the record of what a person signed and it outlives the program that wrote it. Leave it, and say so in the uninstall UI so nobody thinks it vanished. If you disagree, argue it in a decision rather than deleting it.

Configuration and pairings: decide, and record which way and why.

Verify by hash that nothing else on the machine changed — the discipline every phase has applied to itself, applied now to the product.

## 4. Signing the release

There is no code-signing certificate, and SPEC §15.1 says not to design around its permanent absence.

- **The build pipeline contains an Authenticode signing step that is currently a no-op.** It exists, it is wired in, and filling in a certificate later changes nothing else. A step that is absent is not the same as a step that does nothing.
- **"Signed package" means our own signature** (SPEC §15.2). The agent embeds a public key; every release is signed with the private half; the agent verifies a release before doing anything with it.

### 4.1 The private key needs a home and a story

- Never in the repository, never in an artefact, never in a log. F8 already had one secret leak; the same care applies here, where the consequence is larger.
- The signing job must not be reachable from a fork's pull request.
- **What happens if the key is lost or compromised.** Every installed agent trusts a key it cannot be told to stop trusting. State the answer — reinstall by hand, a second embedded slot, something else — and record it. An unanswered version of this question is discovered at the worst possible moment.

---

## 5. The update check

Per SPEC §15.2 and §6.8:

- GitHub Releases, once per day, disableable in settings.
- Verifies the signature before doing anything with what it downloaded.
- **Asks the user. Never installs by itself.** This is the consent principle in another costume and it deserves the same suspicion: no flag, no configuration key, no silent mode. F9 found one of these four phases after it shipped.
- It is one of exactly four outbound requests this program is allowed to make (§6.8). It must not send anything about the user or the machine — no identifier, no version telemetry beyond what a plain release fetch unavoidably reveals. Say what it sends.
- **Offline is normal, not an error.** A machine with no internet signs documents with no complaint beyond what §6.8 already allows.

---

## 6. The user guide

For signers, not developers. SPEC §9.1's three locales govern what non-developers read; decide whether the guide ships in all three or in `sr-Latn` only, and record it.

It must contain, because the stranger will meet all of them:

- **The SmartScreen warning, with a screenshot, and what to click.** SPEC §15.1 requires this explicitly.
- **What to do if antivirus quarantines it.** An unsigned executable that talks to a smart card and opens a local port is a textbook false positive, and the person it happens to will not guess.
- **Reader and middleware** — what must already be present for a card to be seen at all, per issuer.
- **The first signature, start to finish, with pictures.**
- **Where the audit log is and what it is for.**
- **How to uninstall.**

Written for somebody who has an invoice to sign and forty minutes of patience, not for somebody who reads a README.

## 7. Carried over

`TestALongApplicationNameStaysReadableInThePairingWindow` failed once in F9b on a one-pixel difference after a WebView2 resize, and passed on re-run.

This phase makes CI the thing that builds releases, so a test that fails one run in ten becomes a release that fails one attempt in ten, and a suite people learn to re-run instead of read. Find out whether the resize wait observes the resize or waits a fixed time. Fix it, or record why it is sound. Do not raise a timeout.

## Rules

This phase only. No new capability, no other platform, no protocol change.

**Verify by installing and running, not by inspecting what the build produced.** An MSI that passes its own validation and fails on a machine is this project's failure mode wearing a new hat — recorded four times (D-161, D-200, D-219, D-221).

**Test on a machine or image that has never had a Go toolchain, and on a standard user account with no administrative rights.** D-234's lesson is one phase old: a development account's token looks like a user's and is not one.

No synthetic mouse or keyboard input (D-094). Never kill processes by image name; exact PID only. A test asserting a property must observe the property, not time how long the machine took (D-201). Every existing test passes; no `//nolint`.

Full Go suite with `-count=1` on Windows, with and without `softtoken`. The TypeScript suite on both platforms.

Record a decision for every choice above that says *decide and record*, plus whatever the WebView2 investigation turns up.

---

## Exit condition, and the part that is not the builder's

The phase ends when a stranger installs it and signs a document. Neither the agent nor the owner can be that stranger.

What this phase delivers is everything up to that point, plus the thing that makes it possible: **a written walkthrough of exactly what that person will do**, from the download link to a signed PDF, with the failure points named — the SmartScreen dialog, a missing WebView2 runtime, a reader with no driver, a card the middleware does not see. At each one, what they will see and what they should do.

Then report what could be verified and what could not, without blurring the line between them. *Installed and signed on a clean VM under a standard account* is a real result and worth having. It is not the exit condition, and the report must not let it read as one.
