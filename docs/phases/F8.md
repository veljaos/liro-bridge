# Phase F8 — The TypeScript SDK

**Prerequisite reading:** `docs/SPEC.md` in full, `docs/decisions.md` in full, and `docs/PROTOCOL.md` in full — the last one is the specification you are implementing against.

**Prerequisite phase:** F7 complete and verified end to end. A PowerShell client written against `PROTOCOL.md` alone paired, submitted a document and received a signature made with a real MUP card. `GET /v2/certificates`, `POST /v2/echo` and the `origin` documentation came out of writing that client.

**Goal of this phase:** an integrator adds signing to their application in three lines and does not learn what HMAC is.

**Explicitly not in this phase:** no installer, no macOS, no Linux, no changes to the agent's own behaviour. If the SDK cannot do something because the protocol will not let it, that is a finding to report — not a licence to change the protocol.

---

## 0. What the owner decided

**TypeScript is the only first-class SDK.** Other languages get short examples in the README, not packages.

**It is not published to npm.** It lives in this repository and integrators install it straight from GitHub. That removes a class of risk — nobody can squat a similar name or take over an abandoned package — and it removes the versioning apparatus. It does not remove the need for the code to be careful.

**Security is not traded for convenience anywhere.** The device secret is the whole of an application's authority to ask for a signature. An SDK that makes it easy to put that secret somewhere wrong is worse than no SDK.

---

## 1. What the integrator writes

This is the target, and the measure of whether the phase succeeded:

```typescript
import { LiroBridge } from '@liro/bridge';

const bridge = await LiroBridge.connect({ applicationName: 'Moj ERP' });
const signed = await bridge.signPdf(pdfBytes);
```

Everything else is the SDK's problem: finding the agent, pairing, storing the secret, the canonical string, nonces, the job, the event stream, the timeouts, and turning error codes into typed exceptions.

**If the README's first example needs more than five lines, the SDK is wrong** — SPEC §20. Fix the SDK, not the example.

---

## 2. Where it lives and how it is installed

```
sdk/typescript/
```

Installed from GitHub:

```bash
npm install github:veljaos/liro-bridge#main --workspace-root
```

or, more usefully for an integrator who wants a fixed version, pinned to a tag.

Requirements:

- **ESM, with CommonJS output alongside it.** A great deal of Serbian ERP work is on older Node and `require` must work.
- **TypeScript types shipped**, generated from the source rather than hand-written.
- **Zero runtime dependencies.** Node's own `crypto`, `fs` and `fetch` cover everything. Every dependency added here is a dependency in the integrator's application, in a package that handles a signing secret.
- Node 18 or later. Say so, and fail with a clear message on older versions rather than at some random point later.

The build produces committed output, because installing from GitHub means there is no publish step to run it. Say plainly in the README how to rebuild it, and add a CI check that the committed output matches the source — this project has already had one generated file drift from its generator (`scripts/synctokens`, which deleted a block five screens depended on).

## 3. Pairing

The first call does it, and the flow is the awkward part of the protocol made bearable.

```typescript
const bridge = await LiroBridge.connect({
  applicationName: 'Moj ERP',
  origin: 'https://erp.example.com',
  onPairingCode: () => {
    // The agent is showing a six-digit code on the user's screen.
    // Get it from them however your application asks questions.
    return promptTheUserForTheCode();
  },
  secretStore: myStore,
});
```

- If a secret is already stored, pairing does not happen and `onPairingCode` is never called.
- If it is not, the SDK calls `pair/request`, invokes `onPairingCode`, and calls `pair/confirm` with **the same `origin` in both** — the thing that cost the owner time writing the first client by hand.
- Wrong code: the SDK reports how many attempts remain, from `details.attemptsRemaining`, and lets the caller ask again without starting over.
- Five minutes expire, five wrong codes, another application's window already open: each becomes its own typed error with a message saying what to do.

**`secretStore` is required and has no default.** Not a file path with a sensible fallback, not "we'll put it in `~/.liro`". The SDK does not choose where a signing secret lives — the integrator does, deliberately, and the type system makes them.

```typescript
interface SecretStore {
  get(appName: string): Promise<StoredPairing | null>;
  set(appName: string, pairing: StoredPairing): Promise<void>;
  clear(appName: string): Promise<void>;
}
```

Ship one implementation, `FileSecretStore`, which writes to a path the caller names, with `0600` on POSIX and the equivalent on Windows. Document that a database or a secrets manager is better for a server application, and that the file store exists so a first integration works.

## 4. Security, which is most of the value here

### 4.1 The secret never reaches a browser

State it in the README's first section, not in a note at the end. The device secret is an application's authority to ask for a signature. In a page it belongs to everyone who visits.

The agent already refuses browsers: no CORS headers, `OPTIONS` returns 403. The SDK must not appear to work around that. **If it detects it is running in a browser, refuse to construct at all**, with a message naming the reason. A developer who tries it should be stopped in ten seconds rather than after building a feature around it.

### 4.2 The secret never reaches a log

Not in a thrown error, not in a debug mode, not in `toString`, not in anything the SDK serialises. Add a test that pairs, exercises every error path, and greps every string the SDK produced — messages, stacks, debug output — for the secret and for its base64 form.

`StoredPairing` should keep the secret out of enumerable properties, or behind an accessor, so that `console.log(pairing)` and `JSON.stringify(pairing)` do not print it. Test both.

### 4.3 Nonces

Generated with `crypto.randomUUID()` or `crypto.randomBytes`, never with `Math.random()`. Never reused, including across retries — a retried request needs a new nonce, and forgetting that produces `AUTH_FAILED` on the retry, which is the least helpful message the protocol has.

### 4.4 Retries

Retry only what is safe to retry: a connection that never opened, a `5xx`, a timeout with no response. **Never retry a `401`**, and never retry a submission that may have created a job — a duplicate batch is a hundred documents signed twice.

**`PIN_INCORRECT` is never retried automatically, in any circumstance.** Three wrong entries block a card; for a national identity card, unblocking means a visit to the Ministry. The README says this in the strongest terms the language allows.

### 4.5 What the SDK verifies

The signed document that comes back was produced by the agent and approved by a person, so the SDK does not need to validate it. But it should confirm the obvious: that the number of documents returned matches the number sent, and that a returned document is not empty. A mismatch is a bug somewhere and silence is the wrong response to it.

## 5. The API

Small, and shaped by what an integrator actually does.

```typescript
class LiroBridge {
  static async connect(options: ConnectOptions): Promise<LiroBridge>;

  async health(): Promise<Health>;
  async certificates(): Promise<Certificate[]>;

  async signPdf(
    documents: Uint8Array | Uint8Array[] | Document[],
    options?: SignOptions,
  ): Promise<SignedDocument[]>;

  async signDigests(
    digests: Uint8Array[],
    options: SignDigestsOptions,      // certificateThumbprint required
  ): Promise<Signature[]>;

  onProgress(handler: (p: Progress) => void): void;

  async disconnect(): Promise<void>;   // forgets the local secret
}
```

Notes:

- **`signPdf` takes bytes and returns bytes.** The common case is one document, and `signPdf(buffer)` must work without wrapping it in anything.
- `certificates()` maps straight onto `GET /v2/certificates`. It may return `CERTIFICATE_LISTING_DISABLED`, which is a setting on the machine, not an error in the caller — the message must say that.
- **`signDigests` requires `certificateThumbprint`**, and `PROTOCOL.md` §5.5 records the hole this leaves: a caller that has never seen the certificate cannot build a CMS around it. Do not paper over it. Document it where `signDigests` is documented, and say what a caller can do today: list the certificates, let the person choose, build the CMS around that one.
- **`onProgress` is optional and everything works without it.** Someone signing one document should not have to think about a stream.
- The `awaiting_consent` event carries the remaining time; surface it, because an ERP wants to show its own countdown.
- The `preparing_card` state matters: four seconds on a MUP card, twelve on a Pošta card, measured. Say in the types and in the README that this state is expected and not a stall.

## 6. Errors

Every code in `PROTOCOL.md`'s tables becomes a typed error carrying `code` and `details`, and the union is exhaustive so that a `switch` over it is checkable.

```typescript
try {
  await bridge.signPdf(pdf);
} catch (e) {
  if (e instanceof LiroError && e.code === 'CARD_NOT_PRESENT') {
    // tell the user to insert their card
  }
}
```

Two things the message text must do:

**`AUTH_FAILED` says to look at the agent's log.** It is the only place that says which check refused — `signature_mismatch`, `clock_skew`, `origin_mismatch`, `nonce_reused` — and D-175 settled that the response never will. That one sentence saves an integrator a morning; it saved the owner one.

**It should also mention `POST /v2/echo`**, which returns the canonical string the agent built. An integrator prints their own beside it and sees the difference in one line.

- How to rebuild the committed output.

Serbian ERP developers read English documentation daily. **Write it in English**, like the rest of the project.

## 8. The other languages

Roughly twenty lines each, in the README, not packages: **C#, Python, Java, PHP**. Add Go if it costs nothing — the agent is written in it and someone will ask.

Each shows: read `bridge.json`, build the canonical string, sign it, submit, poll. Enough that a competent developer sees the shape and writes the rest.

`liro-test-client.ps1` at the repository root is the PowerShell version of exactly this, written against `PROTOCOL.md` and proven against a real card. **Move it to `sdk/examples/` and make it one of them.**

Each example must be **run before it is committed**, against the real agent, with the soft token. An example that does not run is worse than no example — it costs the reader more than writing it themselves. Report which you ran and what they produced.

The four failures that writing the PowerShell client produced are the ones every example must avoid by construction: a wrong field name, `origin` missing from `pair/confirm`, a body altered between hashing and sending, and a `Content-Type` .NET cannot put on a GET.

## 9. Testing

- Unit tests over the canonical string, against `PROTOCOL.md`'s worked example — the same example the agent's own test pins. Both must agree with the document.
- Every error code mapped and thrown, exhaustively.
- **Against a real agent**: pair, list certificates, sign with the soft token, receive bytes, verify the count.
- Browser detection refuses.
- The secret never appears in any string the SDK produces.
- A retried request uses a new nonce.
- `401` is never retried.
- The committed build output matches the source.

---

## Rules

- This phase only. No installer, no other platforms, no changes to the agent.
- **Verify by running the SDK against the built agent**, not only by running tests. A protocol client that passes its tests and fails a real request is this project's recurring failure mode, and it has happened with two hand-written clients already.
- **No synthetic mouse or keyboard input, ever** — D-094. Pairing needs a human to read a code; drive it with the code read from the agent's own state, or ask the owner.
- **Never kill processes by image name** — exact PID only.
- **Leave the machine as you found it** — snapshot and verify `config.json`, the audit directory, `HKCU\...\Run` and the Explorer verb by hash.
- **A test asserting a property must observe the property, not time how long the machine took** — D-201.
- Every existing test passes. No `//nolint`, and no `eslint-disable` either.
- Record a decision for each judgment call, in `docs/decisions.md`'s existing format.

Run the full Go suite with `-count=1` on Windows, with and without `softtoken`, plus whatever the TypeScript side needs.

**Report:** the README's first example exactly as it will be read; what `secretStore` looks like for someone with no strong opinion; which language examples you ran and what they produced; and anything in `PROTOCOL.md` that turned out to be wrong, missing or misleading when something other than PowerShell tried to use it.
