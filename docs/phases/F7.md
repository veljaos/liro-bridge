# Phase F7 — The protocol

**Prerequisite reading:** `docs/SPEC.md` in full, then `docs/decisions.md` in full.

**Prerequisite phase:** F6b complete, and both FTEST groups run. The product signs PDFs with Serbian qualified certificates in one window, verified against real hardware from two issuers, with sixteen defects found and fixed by testing.

**Goal of this phase:** any program on the machine can ask the agent to sign, and the person approves it in the agent's own window.

**This is the second hardest phase after F3**, but it fails differently. A mistake here produces a rejected request, not a silently invalid signature. That makes it far easier to hunt than what F3 went through.

**Explicitly not in this phase:** no SDK — that is F8. No installer, no macOS, no Linux. Nothing that changes how the signing engine works.

---

## 0. What the owner decided

Four questions, answered before this document was written. They are settled.

**Any program on the machine may pair, with the user's approval.** Not a whitelist the owner maintains. This is the Stripe-level ease he asked for: an integrator writes code, the user approves once, it works.

**One approval covers a whole batch.** A hundred documents from an ERP is one window and one PIN, exactly as a hundred documents dropped by hand.

**Both signing paths stay.** Hashes for callers who can build CMS themselves, whole documents for callers who cannot. Flexibility matters more here than minimalism.

**The consent window waits, then expires.** The request is not refused because nobody is at the machine; the window opens and waits. See §7.4 for the number and why.

---

## 1. What already worked

The previous Bridge had a working protocol and its document survives in the old repository. Where it was right, keep it. The reference implementation is in `internal/api`, `internal/auth`, `internal/session` and `internal/job` of that repository, which the owner has kept.

**Do not copy that code.** Read it where a detail is unclear, then write this from the specification. Three of the seven defects that cost this project the most were inherited assumptions that nobody re-derived.

Carried forward unchanged, because it was right:

- The canonical string and the four headers
- `202 Accepted` with a job, progress over a stream, result fetched separately
- The result is delivered once and then forgotten
- A batch fingerprint returned at submission so the caller can compare
- Never retrying after a wrong PIN

Changed, and each change has a reason below: port discovery, multi-session behaviour, the error-code vocabulary, a second signing endpoint, and what the request may say about the stamp.

## 2. Pairing

### 2.1 The six-digit code

The old design is better than what SPEC §6.2 sketches and replaces it.

1. The application calls `POST /v2/pair/request` with a display name.
2. The agent opens a window showing a **six-digit code**.
3. **The code is not in the response.** If it were, an application could pair itself without a human ever seeing the window.
4. The person reads the code from the agent's window and gives it to the application, which submits it to `POST /v2/pair/confirm`.
5. The agent issues a **device secret** — 32 random bytes — exactly once.

That the code travels through the human is the whole point. It proves a person was present, and no amount of access to the loopback interface substitutes for it.

Requirements:

- The code expires in **five minutes**.
- **Five wrong attempts void the request**, and a new one must be started.
- Confirm must arrive from the same origin as the request.
- The secret is returned once. A second call to confirm the same request fails.
- The pairing window shows the application's name and its origin **verbatim** — no prettifying, no stripping of the scheme, and with the same untrusted-input handling file names get in the consent window (SPEC §6.6). A user who sees `http://` instead of `https://` must be able to notice.

### 2.2 What is bound

The secret is bound to the origin at pairing time. A secret issued to `https://app.example.com` is useless from anywhere else.

**The application's display name comes from pairing, never from a later request.** SPEC §6.6 already requires this and F5 implements it: otherwise an application pairs as "Test" and later presents itself as "Liro".

### 2.3 Where the secret lives

**On the integrator's server, never in a browser.** Document this prominently: not in `localStorage`, not in code shipped to a page. A secret in a browser is a secret every visitor has.

### 2.4 Managing pairings

Settings gains a list of paired applications: name, origin, when paired, when last used, and a way to revoke. Revoking is immediate.

## 3. Request authentication

Every call to a protected endpoint carries four headers:

```
X-Liro-App-Id      <appId>
X-Liro-Timestamp   <unix seconds>
X-Liro-Nonce       <unique per request>
X-Liro-Signature   <hex HMAC-SHA256, lowercase>
```

The signed string, with `\n` as the separator and nothing else:

```
METHOD \n PATH \n TIMESTAMP \n NONCE \n SHA256HEX(BODY)
```

- `METHOD` uppercase.
- `PATH` without the query string.
- `SHA256HEX(BODY)` over the raw bytes, lowercase hex. An empty body hashes to `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`, which is worth stating in the documentation because every integrator gets it wrong once.

The signature is `HMAC-SHA256(deviceSecret, canonicalString)`.

Rejections:

- Timestamp outside **±60 seconds**
- Nonce seen in the last **five minutes**
- Signature mismatch, compared in constant time

A rejection returns `401` and a code. **It never says which check failed** — that is a hint to whoever is probing.

The body hash is computed over the bytes as received, before parsing.

## 4. Finding the agent

### 4.1 Ports and discovery

The old protocol hardcoded 17580. That breaks the moment two people share a machine.

The agent binds **loopback only** on the first free port in **17580–17590**, and writes what it chose to a per-user file:

```
Windows   %LOCALAPPDATA%\Liro\bridge.json
```

The file carries the port, the agent version, and the protocol version.

**SDKs and integrators read this file. They must never scan ports.** Scanning finds another user's agent on a shared machine, which is exactly what §4.2 exists to prevent.

### 4.2 Several people on one machine

Accounting firms run several users on one machine over RDP. This is a supported configuration and not an edge case.

- **One agent per user session**, not per machine.
- The discovery file is per user, so each session finds its own agent.
- Sessions must not see each other's certificates, pairings, jobs or audit entries.
- Binding to loopback does not separate sessions by itself — loopback is shared. Separation comes from the per-user discovery file and from the device secret being stored per user (SPEC §6.4).

Test with two real sessions, not with two processes under one account.

### 4.3 Health

`GET /v2/health` needs no authentication and returns the agent version, the protocol version, and the **minimum client version** the agent will accept. It reveals nothing else — not certificates, not pairings, not the user's name.

## 5. Signing with hashes

`POST /v2/sign`

For callers that build the PDF and the CMS themselves. The agent never sees the document. This is SPEC §4.3's first entry and the property that makes a compromised web application unable to extract documents through the agent.

```json
{
  "certificateThumbprint": "7758D4...",
  "digestAlgorithm": "SHA256",
  "digests": ["<base64>", "..."],
  "labels": ["ugovor.pdf", "..."]
}
```

- At most **500 digests** per request.
- Each digest's length must match the algorithm — 32 bytes for SHA-256 — and is validated before anything else happens.
- `labels` are display strings for the consent window. They are untrusted input (SPEC §6.6), are never treated as paths, and are never logged.
- SHA-1 is not accepted. SPEC §18.8.

---

## 6. Signing whole documents

`POST /v2/sign/pdf`

For callers that cannot build CMS — an ERP in Delphi, C# or Java. The agent receives the document, signs it, and returns it.

```json
{
  "certificateThumbprint": "7758D4...",
  "documents": [ { "name": "ugovor.pdf", "content": "<base64>" } ],
  "level": "b-t",
  "stamp": { "visible": true, "position": "bottom-right" }
}
```

- **Optional at install time.** The installer offers to leave it out, and Settings can disable it. A deployment that only serves Liro's own applications does not need it.
- The audit entry records that this path was used, distinctly from the hash path.
- Size limits: 100 MB per document, 500 MB per request, 200 documents per request. State them in the documentation and enforce them before reading the body into memory.
- When `stamp` is supplied in full, the consent window shows only the approval — step 3 is skipped. That is the one-window, one-click case the owner asked for, and F6b's flow was designed for it.
- When `stamp` is absent, the person chooses as they do locally.

## 7. Jobs

### 7.1 Why

A hundred documents takes about 46 seconds after the PIN. No HTTP request should be held open that long.

Submission returns `202 Accepted` within milliseconds:

```json
{
  "jobId": "...",
  "batchFingerprint": "d54aeba8...",
  "total": 100,
  "eventsUrl": "/v2/jobs/<id>/events",
  "resultUrl": "/v2/jobs/<id>/result"
}
```

`batchFingerprint` is SHA-256 over the concatenated digests, the same value the consent window shows, so a technical user can compare what was approved against what was sent.

### 7.2 Progress

`GET /v2/jobs/{id}/events`, server-sent events.

```json
{"state":"signing","completed":37,"total":100,"failed":0,"etaMs":26000}
```

States: `queued`, `awaiting_consent`, `awaiting_pin`, `preparing_card`, `signing`, `completed`, `failed`.

`preparing_card` is new and matters: SPEC §12.9 measured 4.0 s on a MUP card and 12.7 s on a Pošta card before the first signature. A caller showing a progress bar needs to know that period is expected rather than stalled.

`etaMs` is computed from the measured first signature, never from a constant.

Document that browsers cannot use `EventSource` here, because it cannot set headers, and that `fetch` with a `ReadableStream` is the way.

### 7.3 Result

`GET /v2/jobs/{id}/result` returns `202` with current counts while running, and `200` with the signatures when finished.

**The result is delivered once and the job is then forgotten.** A second call returns `404`. Signatures are the output of a qualified signing operation and do not linger in a process's memory waiting to be collected twice.

A job whose result is never collected is discarded after **ten minutes**.

### 7.4 The consent timeout

**120 seconds**, and the reason is consistency rather than taste: F2 already established a 120-second approval-to-first-signature window, and inventing a second number for the same human decision would mean two answers to one question — the pattern this project has removed three times.

- The window shows a countdown in the **last 30 seconds**, so the person sees it is about to expire rather than finding it gone.
- On expiry the job fails with `CONSENT_TIMEOUT`, and the caller can resubmit.
- The remaining time is included in the `awaiting_consent` event, so an ERP can show its own state.
- The window is topmost and takes focus. A consent request nobody sees is a consent request that times out.

## 8. Errors over the wire

The old protocol used lowercase codes of its own. **This one uses `internal/errs`** — the same `SCREAMING_SNAKE_CASE` vocabulary the CLI and the windows already speak, with messages in all three catalogues and a test that fails if any code lacks one.

Two vocabularies for one set of conditions is exactly what SPEC §7 exists to prevent.

```json
{ "code": "CARD_NOT_PRESENT", "details": { "reader": "..." } }
```

No human-readable message crosses the API, in any language. SPEC §7.

Some conditions need codes the local paths never produced — `NOT_PAIRED`, `AUTH_FAILED`, `NONCE_REUSED`, `TIMESTAMP_SKEW`, `VERSION_TOO_OLD`. Several already exist; add what is missing and document every code a caller can receive.

**`PIN_INCORRECT` must never be retried automatically**, and the documentation must say so in the strongest terms available. Three wrong entries block a card. For a national identity card, unblocking means a visit to the Ministry.

---

## 9. The consent window in this flow

Nothing about SPEC §6.5 changes because the request came over HTTP. The card caches the PIN independently of our process; the human pressing Approve is still the only thing that reliably prevents an unauthorised signature.

- The application's name is the one bound at pairing.
- The document count and, where labels were supplied, the file list — sanitised as in SPEC §6.6.
- The batch fingerprint behind Details.
- Certificate selection is explicit, with no "remember last used". SPEC §18.15.
- Approve is not the initially focused control.

A request from a paired application is not more trusted than a person dropping files. It is the same window.

---

## 10. Rate limiting

An unpaired caller can hit `/v2/pair/request` in a loop and open windows without end.

- At most **one pending pairing request at a time**. A second while one is open is refused.
- At most **three pairing requests per minute** from one origin.
- A paired application may have **one job at a time**. A second submission while one is running is refused with a code.
- Nonce cache and skew window already bound replay.

---

## 11. What must not happen

- No request may reach the signing engine without a human approval. No flag, no header, no configuration.
- The hash endpoint must never receive a document, and `internal/pades` must never import `internal/api` — the lint rule in `scripts/checkdeps` already enforces the second and must keep passing.
- No secret, no PIN, no document content, no file name and no personal name in any log line. SPEC §18.3.
- No listening socket other than the loopback one. Binding to a non-loopback interface must be impossible, not merely off by default.
- The protocol must not require the caller to trust the agent with anything it does not need.

## 12. Testing

Beyond the usual, this phase needs:

**Authentication that fails.** A wrong signature, a stale timestamp, a future timestamp, a reused nonce, an empty body signed as if it had content, a body altered after signing, a signature from another application's secret, a request to a path other than the one signed. Every one refused, and none of them telling the caller which check failed.

**Pairing that fails.** A wrong code five times, an expired request, confirm from a different origin, confirm twice, two requests at once.

**Sessions.** Two real user sessions, each with its own agent, each finding its own port, neither seeing the other's pairings or jobs.

**Jobs.** Result collected twice. Result never collected. Events stream disconnected mid-batch and reconnected. A job submitted while another runs.

**The consent path.** Denied. Expired. The window closed. The card removed mid-batch. All the way through to a caller receiving a coherent answer.

**Both signing paths**, producing signatures that the independent verifier accepts, over the three real fixtures.

**A hundred documents end to end** through the protocol, one PIN, timing recorded.

And, as always: **verify by running the built binary.** A protocol that passes its tests and refuses a real request from a real program is this project's recurring failure mode.

## Rules

- This phase only. No SDK, no installer, no other platform.
- **No synthetic mouse or keyboard input, ever** — D-094.
- **Never kill processes by image name** — exact PID only.
- **Leave the machine as you found it** — snapshot and verify `config.json`, the audit directory, `HKCU\...\Run` and the Explorer verb.
- **Verify by running the built binary**, with a real client, not only by running tests.
- Every colour from a token; `checkcss` green. Every new string in all three catalogues; help and usage English.
- Every existing test passes. No `//nolint`. Never weaken an assertion to make something pass — five recorded instances in this project have a green suite accompanying a broken product.

Run the full check suite with `-count=1`, on Windows, with and without the `softtoken` tag.

**Report:** the canonical string with a worked example an integrator can check against; what happens when two sessions run on one machine; the timing of a hundred documents through the protocol against the same hundred locally; and what a caller sees for each way authentication can fail.
