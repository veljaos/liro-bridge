# Phase F3 — The PAdES engine

**Prerequisite reading:** `docs/SPEC.md` in full, with §12 (PAdES rules) memorised, then `docs/decisions.md` in full.

**Prerequisite phase:** F2 complete. In particular, OpenSSL must already report `Verified OK` for a signature produced by `sign-digest`. If that is not true, stop — every failure in this phase would have two possible causes.

**Goal of this phase:** turn a PDF and a signing session into a signed PDF that Adobe accepts and that an independent validator accepts.

**This is the hardest and riskiest phase in the project.** It deliberately precedes all UI work. If `/ByteRange` is wrong, everything built above it is wasted.

**Explicitly not in this phase:** no visual stamp (F4), no windows (F5), no drag and drop (F6), no HTTP (F7).

**Exit condition:** `liro-bridge sign --in x.pdf --out y.pdf` produces a document that Adobe Reader reports as not modified since signing, that the PKS validation service accepts, and that our own independent verifier accepts — and signing an already-signed document leaves the earlier signature valid.

---

## 1. Build order

Five parts. Each has tests that pass before the next exists. Do not reorder.

1. **PDF object model and parser** — read a document, resolve objects.
2. **Incremental update writer** — append a revision without touching existing bytes.
3. **Signature placeholder** — reserve space, compute `/ByteRange`.
4. **CMS construction** — build SignedData over the document digest.
5. **Timestamp and DSS** — B-T, then B-LT.

---

## 2. PDF parsing

**Package:** `internal/pades/pdf`

### 2.1 Both cross-reference mechanisms are mandatory

Measured on the three fixtures in `testdata/pdfs/`:

| Fixture | xref tables | xref streams | object streams |
|---|---|---|---|
| Halcom | 3 classic | 0 | 0 |
| MUP | — | 4 | 4 |
| Pošta | — | 4 | 1 |

**Two of the three real documents use cross-reference streams and object streams.** A parser supporting only classic `xref` tables opens one document in three. Both mechanisms are required from the start; neither is a later refinement.

- **Classic table:** `xref` keyword, subsection headers, 20-byte entries, `trailer` dictionary.
- **Cross-reference stream (PDF 1.5+):** a stream object with `/Type /XRef`, `/W` field widths, `/Index` subsections, `/Size`, and the trailer keys inside the stream dictionary. Entry type 0 free, 1 in-file, **2 inside an object stream**.
- **Object stream:** `/Type /ObjStm`, `/N` object count, `/First` offset to the payload, then N pairs of object number and relative offset, then the objects themselves, all inside the compressed stream.

All fixtures have multiple revisions (`/Prev` chains). Follow the chain to the beginning and merge, with **later revisions taking precedence**. A hybrid file may have both an `xref` table and an `/XRefStm` pointer; handle it or reject it explicitly, but do not misread it.

### 2.2 Lexer and objects

The full object grammar: null, boolean, integer, real, string (literal `()` with escapes and balanced parentheses, and hex `<>`), name (with `#xx` escapes), array, dictionary, stream, indirect reference.

Traps that will bite:

- **Names with `#` escapes.** `/A#20B` is the name `A B`. Common in scanned documents.
- **Literal strings contain balanced parentheses** without escaping. Count depth; do not stop at the first `)`.
- **`/Length` in a stream dictionary may be an indirect reference**, which means you cannot know the stream length without resolving another object — which may itself be after the stream. Fall back to scanning for `endstream` when resolution is not yet possible.
- **Line endings are inconsistent.** The MUP and Pošta fixtures use `\r` after the header; Halcom uses `\n`. Accept `\r`, `\n` and `\r\n` everywhere.
- **`startxref` may point at a wrong offset** in a repaired file. If the offset does not yield a valid xref, fall back to scanning the file for `obj` markers and rebuild. Real-world documents need this more often than they should.

### 2.3 Encryption

If the trailer contains `/Encrypt`, return `errs.CodePDFEncrypted` and stop. **Do not implement decryption.** None of the fixtures are encrypted, and signing an encrypted document is a separate feature with its own risks.

### 2.4 Size limits

Reject input larger than **512 MB** with `CodePDFInvalid`. Documents that size in a signing agent are a mistake or an attack, and the parser holds the file in memory.

### 2.5 Tests

- Parse all three fixtures; enumerate every object; resolve every indirect reference.
- Object-stream extraction: an object inside an `ObjStm` resolves identically to a direct object.
- Multi-revision merge: the newest definition of an object wins.
- Lexer table: `#`-escaped names, nested parentheses, hex strings with odd digit counts, real numbers in every notation, an indirect `/Length`.
- Corrupt `startxref` triggers the rebuild path and still parses.
- An encrypted document returns `CodePDFEncrypted`.
- **Fuzz the parser.** It accepts foreign input. No panic, no unbounded allocation, no infinite loop. This is required by SPEC §16.5 and is not optional.

## 3. Incremental update

**Package:** `internal/pades/pdf`, file `incremental.go`

### 3.1 The rule that makes signatures survive

**Original bytes are never modified.** The output is the input, byte for byte, followed by appended new objects, a new cross-reference section, and a new trailer with `/Prev` pointing at the previous one.

This is what allows the earlier signature to remain valid when a second signer signs: the earlier `/ByteRange` still covers exactly the same bytes it covered before.

```
[ original file, unchanged, byte for byte ]
[ new objects: signature dict, annotation, updated AcroForm, updated page ]
[ new xref section ]
[ new trailer with /Prev = previous startxref ]
startxref
<offset>
%%EOF
```

### 3.2 Match the document's own mechanism

If the previous revision used a classic `xref` table, append a classic table. If it used a cross-reference stream, append a cross-reference stream. **Do not mix.** A classic table appended to a stream-based document is accepted by some readers and rejected by others, which is the worst kind of bug.

This means the Halcom fixture exercises the classic path and the MUP and Pošta fixtures exercise the stream path. All three must round-trip.

### 3.3 Objects to append

- The signature dictionary
- A widget annotation for the signature field, `/Rect [0 0 0 0]` when invisible
- The `/AcroForm` dictionary, with the new field added to `/Fields` and `/SigFlags` set to 3
- The page object, with the annotation added to `/Annots`
- The catalog, if `/AcroForm` had to be added to it

Copy each object being modified in full and append the modified copy. Never edit in place.

### 3.4 Tests

- Append a trivial object to each fixture; the output parses and the original bytes are a prefix of the output. Assert that literally: `bytes.HasPrefix(out, in)`.
- Classic-table document produces a classic table; stream document produces a stream.
- Round-trip all three fixtures through parse, append, reparse.
- The existing signature in each fixture **still verifies** after an unrelated incremental update.

## 4. The signature placeholder and `/ByteRange`

This is the single most dangerous piece of code in the project. SPEC §12.1 forbids delegating it to a library for exactly this reason.

### 4.1 Why it is dangerous

A wrong `/ByteRange` produces a file that opens without error, displays a signature, and is invalid. There is no crash and no warning. The only way to catch it is to verify externally, every time, in CI.

### 4.2 The mechanism

1. Write the signature dictionary with `/Contents` as a hex string of `N` zeros, and `/ByteRange` as a placeholder of fixed width.
2. Note the byte offsets: `a` = 0, `b` = offset of the `<` opening `/Contents`, `c` = offset just after the closing `>`, `d` = length from `c` to end of file.
3. Rewrite `/ByteRange` in place with the real numbers `[0 b c d]`. **The rewrite must not change the length of the array's textual representation**, or every subsequent offset shifts. Pad with spaces inside the brackets to a fixed width.
4. Digest the file over `[0..b] + [c..c+d]` — that is, everything except the `/Contents` hex string.
5. Build the CMS over that digest, hex-encode it, and write it into the reserved zeros. Pad the remainder with zeros; do not shrink the reservation.

### 4.3 Reservation size — explicit number

**Reserve 32768 bytes**, written as 65536 hex characters.

Reasoning, from the real fixtures: their CMS blobs are 11 917, 10 052 and 14 039 bytes, containing the signer certificate, up to two chain certificates, and a signature timestamp token of roughly 7 KB. The largest is 14 KB. RSA-4096 signer certificates and larger chains push this up; 32 KB leaves more than a 2× margin and costs 32 KB of file size, which is irrelevant.

Make it configurable, and **fail loudly** if the assembled CMS does not fit rather than silently truncating:

```go
if len(cms)*2 > reservedHexLen {
    return errs.WithDetails(errs.CodeSignFailed, err, map[string]any{
        "cmsBytes": len(cms), "reservedBytes": reservedHexLen / 2,
    })
}
```

### 4.4 `/ByteRange` array width

Reserve a fixed width per number so the rewrite is length-neutral. Ten digits per entry supports files up to 9.9 GB, far beyond the 512 MB input limit:

```
/ByteRange [0000000000 0000000000 0000000000 0000000000]
```

Write the real values right-aligned within the same width, space-padded. Some validators dislike leading zeros in the final values, so use spaces, not zeros, in the finished file.

### 4.5 Tests — the ones that matter most

- **Byte-exact golden file:** with a fixed test key and a fixed timestamp, the output matches a stored reference exactly. This is what catches an accidental structural change that still happens to verify.
- **`/ByteRange` covers the whole file except `/Contents`:** assert `b + (d - c) + (c - b) == len(file)` and that the excluded span is exactly the hex string including its delimiters.
- **`messageDigest` equals SHA-256 over the `/ByteRange` span**, computed by test code that reads the offsets out of the output file rather than reusing the signing code's variables. Reusing them would make the test circular.
- **Tampering test:** flip one byte inside the signed range; verification must fail. Flip one byte inside `/Contents`; verification must fail. This is the security-check-that-must-fire discipline from F1 and F2.
- **Oversized CMS:** reserve 1024 bytes artificially and assert a clear error rather than a truncated signature.

## 5. CMS

**Package:** `internal/pades/cms`

### 5.1 Exact structure

Copied from SPEC §12.3, itself taken from working documents:

```
SignedData
  version: 1
  digestAlgorithms: { SHA-256 }
  encapContentInfo: id-data, no content (detached)
  certificates: signer + chain
  signerInfos:
    sid: issuerAndSerialNumber
    digestAlgorithm: SHA-256
    signedAttrs:
      1.2.840.113549.1.9.3    contentType = id-data
      1.2.840.113549.1.9.4    messageDigest = SHA-256(ByteRange)
      1.2.840.113549.1.9.16.2.47  signingCertificateV2
    signatureAlgorithm: sha256WithRSAEncryption
    signature: <from keysource.Session.SignDigest>
    unsignedAttrs:
      1.2.840.113549.1.9.16.2.14  signatureTimeStampToken
```

### 5.2 Two things that are always got wrong

**No `signingTime` attribute.** PAdES takes the time from the timestamp, not the signer's clock. All three reference documents omit it. Adding it is a conformance error, not a harmless extra.

**The signature is computed over the signed attributes re-tagged as `SET OF`.** In the structure the attributes appear with an implicit `[0]` tag (`0xA0`). Before digesting, replace the leading tag byte with `0x31`:

```go
// RFC 5652 §5.4: the signature is computed over the DER encoding of the
// complete SET OF SignedAttributes, not over the implicitly tagged [0]
// form in which they appear inside SignerInfo. Only the leading tag byte
// differs; the length and contents are identical.
encoded := signedAttrs.Bytes()
encoded[0] = 0x31
digest := sha256.Sum256(encoded)
```

A verifier that makes the same mistake will happily accept the result, which is why the independent verifier in §8 must be written from the RFC, not from this code.

### 5.3 `signingCertificateV2`

`ESSCertIDv2` containing the SHA-256 hash of the signer certificate and, optionally, its issuer and serial. Without it a signature can be replayed against a different certificate holding the same key. Not optional.

### 5.4 The certificate chain

Include the signer and every issuer up to but not including the root, when available.

**The MUP case:** SPEC §11.8 established that MUP documents embed only the signer certificate. When the session supplies no chain, complete it from the trust store built in F1, and if that fails, from AIA `caIssuers`.

**The Halcom AIA defect:** its `caIssuers` points at a `.crl` file where a certificate belongs. Check what you actually fetched — try to parse it as a certificate, and on failure log and continue without the chain rather than crashing.

AIA fetching gets a **10-second timeout and one attempt**. It is best-effort; a missing chain degrades the level, it does not fail the signature.

### 5.5 BER on input, DER on output

SPEC §12.5: real timestamp tokens are **BER with indefinite length** (`30 80 …`). Two of your fixtures contain them. A DER-only parser fails on documents signed through the state portal, which is a large share of Serbian documents.

The parser must accept BER. Everything we generate is DER.

Test both directions: parse a BER token from a fixture, and assert our own output is valid DER by round-tripping through a strict parser.

## 6. Timestamps

**Package:** `internal/pades/tsa`

### 6.1 The request

RFC 3161. `certReq: true` so the token carries the TSA certificate. Nonce: 8 random bytes, and **verify it comes back unchanged**.

Imprint algorithm **SHA-256 or better, never SHA-1** (SPEC §12.4). Note that the state portal's own tool uses SHA-1 for document timestamps; that is a defect to be aware of, not a pattern to copy, and Pošta's TSA rejects SHA-1 outright.

### 6.2 Development endpoint

```
https://test-tsa.ca.posta.rs/timestamp1     HTTP Basic: Test.Korisnik / 123456
https://test-tsa.ca.posta.rs/timestamp2     TLS client certificate (PFX), password 1234
```

Implement **both** authentication modes. Production TSAs require client certificates, so exercising only the easy endpoint leaves the harder path untested until it matters.

Content type `application/timestamp-query` on request, `application/timestamp-reply` on response.

### 6.3 Retries — explicit numbers

| Parameter | Value |
|---|---|
| Attempts | **3** |
| Timeout per attempt | **15 seconds** |
| Backoff | **1 s, then 3 s** |
| Total worst case | **~49 seconds** |

Retry only on network errors, timeouts, and HTTP 5xx. **Do not retry** on HTTP 4xx or on an RFC 3161 rejection — those are deterministic and a retry only wastes the user's time.

### 6.4 Failure is never a hang

SPEC §12.8. After three failures, return `CodeTSAUnavailable` with enough detail for the caller to offer the user a choice: save at B-B, visibly marked, or cancel.

**In F3 the CLI takes that choice from a flag**, since there is no UI yet:

```
--on-tsa-failure=abort     (default)
--on-tsa-failure=b-b       save without a timestamp, print a prominent warning
```

Never downgrade silently.

### 6.5 Verifying the token

- Its `messageImprint` matches the digest we sent.
- The nonce matches.
- The TSA certificate chains to a `granted` `TSA/QTST` service in the Trusted List from F1.
- `genTime` is within a sane window of now — **±10 minutes**, allowing for clock skew on both sides.

## 7. DSS and B-LT

**Package:** `internal/pades/dss`

### 7.1 What B-LT adds

A `/DSS` dictionary in the catalog, containing every certificate in the chain, an OCSP response for each non-root certificate, and CRLs where OCSP is unavailable. Optionally a `/VRI` dictionary keyed by signature hash.

This makes the signature verifiable years later, after the OCSP responder is gone. The state's own tool stops at B-T with no `/DSS`; producing B-LT puts our output ahead of it.

### 7.2 Revocation collection

Endpoints from SPEC §11.9 — all three issuers support OCSP, so B-LT is achievable for all of them. Read AIA from the certificate being checked, not from its issuer: MUP's OCSP URL appears only in the end-entity certificate.

| Parameter | Value |
|---|---|
| OCSP timeout | **10 seconds** |
| OCSP attempts | **2** |
| CRL timeout | **30 seconds** (CRLs are large) |
| CRL attempts | **1** |

Collect **after** the signature and the timestamp exist, so the OCSP response postdates the signature — which is what a validator expects.

### 7.3 Degradation is explicit

If revocation data cannot be collected, the output is B-T, not B-LT. Report the achieved level in the command output and in the result structure. Never claim a level that was not reached.

```
Signed: invoice-signed.pdf
  Level:       B-T  (B-LT requested; OCSP unavailable for 1 certificate)
  Timestamp:   RS-GOV TSA-1, 2026-09-01T10:14:22Z
  Certificate: …B3D1ECCE
```

## 8. The independent verifier

**Package:** `internal/pades/verify`

Written **from RFC 5652 and the PAdES specification**, not by reusing the signing code. Shared helpers between signer and verifier defeat the purpose: a bug in a shared helper passes both ways.

It must:

1. Parse `/ByteRange` from the file and recompute SHA-256 over the covered span.
2. Compare it to `messageDigest` in the signed attributes.
3. Re-tag the signed attributes as `SET OF` and verify the RSA signature against the signer certificate's public key.
4. Validate `signingCertificateV2` against the signer certificate.
5. Parse and validate the timestamp token, accepting BER.
6. Build the chain and check it against the Trusted List.

Every signature the agent produces is verified with it in CI before the test passes.

**Evidence that this approach works:** this exact procedure was applied to all three fixtures during specification, and all three verified — `messageDigest` matched the `/ByteRange` digest and the RSA signature over the re-tagged `SET OF` verified, on documents from three different CAs. The verifier's correctness is therefore established independently of ours.

## 9. The `sign` command

```
liro-bridge sign --in <file.pdf> --out <file.pdf> --thumbprint <hex>
                 [--level b-t|b-lt]        default b-lt
                 [--tsa <url>]             default from config
                 [--on-tsa-failure abort|b-b]
                 [--reserve <bytes>]       default 32768
```

Output naming follows SPEC §12.11: `document.pdf` → `document-signed.pdf` when `--out` is absent. **Never overwrite the input.** If the output exists, fail unless `--force`.

Batch form: `--in` accepts a glob, and every document is signed in one session on one PIN, with skip-and-continue on failure per SPEC §12.10.

### 10.2 The already-signed test is the one that matters

SPEC §16.3. If incremental update disturbs the earlier revision by a single byte, the earlier signature breaks. All three fixtures are already signed, so this test exists three times over.

If this test fails, nothing else in the phase matters.

### 10.3 Manual acceptance

- Adobe Reader: "Document has not been modified since signature was applied". Expect **"identity unknown"** for MUP — its CA is not in Adobe's AATL list. Documented, not a bug (SPEC §16.7).
- PKS validation service accepts it.
- Inception validation service accepts it.
- eUprava validator accepts it.
- Sign a document already signed with the real card; both signatures valid in Adobe.

## 11. Decisions to record

- Reservation of 32768 bytes, with the measured CMS sizes as evidence.
- `/ByteRange` written at fixed width, space-padded, and why length-neutral rewriting is mandatory.
- The parser supports both xref mechanisms, with the fixture measurements as evidence.
- Encrypted PDFs are rejected rather than decrypted.
- The verifier is written independently of the signer, and shared helpers are forbidden.
- TSA retry policy: 3 attempts, 15 s timeout, 1 s and 3 s backoff, and why 4xx is not retried.
- OCSP and CRL timeouts, and why revocation is collected after the timestamp.
- Level degradation is reported, never silent.
- BER accepted on input, DER produced on output, with the state-portal observation as evidence.
