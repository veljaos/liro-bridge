# Phase F1 — Certificates and trust

**Prerequisite reading:** `docs/SPEC.md` in full, with particular attention to **§11 (Certificate rules — ground truth)**. That section contains measured facts about Serbian certification authorities. Every one of them will make your code wrong if you ignore it, and wrong in a way that looks like it works.

**Prerequisite phase:** F0 complete, CI green.

**Goal of this phase:** the agent can find every signing certificate on a Windows machine, tell the user which ones are qualified and which ones are usable right now, and prove it from the command line.

**Explicitly not in this phase:** signing anything. No PIN entry. No PDF. No HTTP. No UI. This phase reads and classifies; it never uses a private key.

**Exit condition:** `liro-bridge certs` correctly lists the certificates on a real Serbian e-ID card, marks the signing certificate as qualified, marks the authentication certificate as not usable for signing, and reports honestly when no card is present.

---

## 1. What this phase builds

Four independent pieces, in this order:

1. **`internal/platform`** — smart card reader detection (Windows `winscard`).
2. **`internal/keysource/windowscng`** — certificate enumeration from the Windows store.
3. **`internal/trust/tsl`** — Trusted List fetching, verification, caching, offline operation.
4. **`internal/trust/classify`** — deciding what a certificate is and whether it can sign.

Then a CLI command that puts them together.

Build them in that order. Each has tests that pass without the next one existing.

## 2. Smart card reader detection

**Package:** `internal/platform`, files `smartcard_windows.go` and `smartcard_other.go`.

### 2.1 Why this exists as a separate concern

SPEC §11.10, verified on real hardware: **certificates remain enumerable in the Windows certificate store after the card is removed.** With an empty reader, both Halcom certificates still listed normally.

If presence is inferred from enumeration, the agent offers to sign, the user clicks, the PIN dialog appears, and the operation fails several seconds later. That is the worst available user experience and it is entirely avoidable.

### 2.2 Interface

```go
// ReaderState describes one smart card reader attached to the machine.
type ReaderState struct {
    // Name is the reader name as reported by the OS, e.g.
    // "Generic Smart Card Reader Interface 0".
    Name string

    // CardPresent is true when a card is inserted and powered.
    CardPresent bool

    // ATR is the card's Answer To Reset, empty when no card is present.
    // Useful for identifying the card type; do not rely on it for
    // security decisions.
    ATR []byte
}

// SmartCardService reports on attached readers.
type SmartCardService interface {
    // Readers lists every attached reader and whether it holds a card.
    // Returns an empty slice — not an error — when no reader is attached.
    Readers(ctx context.Context) ([]ReaderState, error)

    // AnyCardPresent is a convenience wrapper: true if at least one
    // reader holds a card.
    AnyCardPresent(ctx context.Context) (bool, error)
}
```

### 2.3 Windows implementation

Via `winscard.dll`, loaded with `windows.NewLazySystemDLL("winscard.dll")`.

| Function | Purpose |
|---|---|
| `SCardEstablishContext` | Scope `SCARD_SCOPE_USER` (0). Returns a context handle. |
| `SCardListReadersW` | Reader names as a multi-string (double-null terminated UTF-16). |
| `SCardGetStatusChangeW` | Card presence and ATR per reader. |
| `SCardReleaseContext` | Always call it. Use `defer`. |

**Traps, all of which have bitten people:**

- **`SCARD_E_NO_READERS_AVAILABLE` (`0x8010002E`) is not an error condition for us.** It means the machine has no reader. Return an empty slice and `nil`. Treating it as an error produces a scary message where a calm "no reader attached" belongs.
- **`SCARD_E_NO_SERVICE` (`0x8010001D`)** means the Smart Card service is stopped. This *is* an error, and it needs its own error code — the user's fix is to start a Windows service, which is completely different from plugging in a reader. Add `CodeSmartCardServiceDown` to `internal/errs`.
- **The reader list is a multi-string**, not a normal string: `"Reader A\0Reader B\0\0"` in UTF-16. Parse it by scanning for the double null. Do not use `windows.UTF16PtrToString`, which stops at the first null and silently gives you one reader.
- **The buffer size call comes first.** Call with a null buffer to learn the required length, allocate, call again. Or use `SCARD_AUTOALLOCATE`, which then requires `SCardFreeMemory`. Pick one and be consistent.
- **The context can go stale** when the service restarts or a reader is unplugged. On `SCARD_E_INVALID_HANDLE` (`0x80100003`), release and re-establish once, then retry. Do not loop.
- **Reader state is a struct array in and out.** `SCardGetStatusChangeW` takes `SCARD_READERSTATE` records, and you must set `dwCurrentState` to `SCARD_STATE_UNAWARE` (0) and pass a timeout of 0 for an immediate, non-blocking read. Passing `INFINITE` here will hang the agent.

Interpret `dwEventState`: `SCARD_STATE_PRESENT` (`0x00000020`) means a card is in. `SCARD_STATE_EMPTY` (`0x00000010`) means it is not.

### 2.4 Other platforms

`smartcard_other.go` with a build constraint returns an empty list and no error. macOS and Linux arrive in phases 12 and 13.

### 2.5 Tests

Hardware-dependent code cannot be unit-tested meaningfully. Do this instead:

- Test the multi-string parser with a table: empty, one reader, three readers, trailing nulls, a name containing a non-ASCII character.
- Test the return-code mapping: `NO_READERS_AVAILABLE` → empty result, `NO_SERVICE` → the new error code, `INVALID_HANDLE` → one retry then failure.
- Put the DLL calls behind a small internal interface so the mapping logic is testable with a fake.

## 3. Certificate enumeration

**Package:** `internal/keysource/windowscng`, file `enumerate_windows.go`.

### 3.1 What it produces

```go
// Certificate is one candidate signing certificate found on this machine.
type Certificate struct {
    // Thumbprint is the SHA-1 hash of the DER certificate, uppercase hex.
    // It is the identifier used everywhere in the agent and in the API.
    Thumbprint string

    // DER is the raw certificate.
    DER []byte

    // Provider is the CNG provider name, e.g.
    // "Microsoft Smart Card Key Storage Provider".
    Provider string

    // OnHardware is true when the key lives on a smart card or token,
    // deduced from the provider (§3.4).
    OnHardware bool

    // KeyContainer is the CNG key container name. Needed later for
    // opening a signing session; carried now so nothing has to
    // re-enumerate.
    KeyContainer string
}
```

Note what is **not** here: no subject, no issuer, no name, no validity. Those come from parsing the DER in `internal/trust/classify`. This package's only job is finding certificates and describing how the key is stored. Keep it that way — it is the difference between a Windows-specific package and a Windows-specific package that has spilled X.509 logic everywhere.

### 3.2 Windows API sequence

Via `crypt32.dll`. `golang.org/x/sys/windows` has some of these; the rest need `NewLazySystemDLL`.

1. `CertOpenSystemStoreW(0, "MY")` — the current user's personal store. **Not `CERT_SYSTEM_STORE_LOCAL_MACHINE`.** Smart card certificates propagate to the user store.
2. `CertEnumCertificatesInStore` in a loop until it returns nil.
3. For each context, `CertGetCertificateContextProperty` with `CERT_KEY_PROV_INFO_PROP_ID` (2), which yields a `CRYPT_KEY_PROV_INFO`:
   - `pwszProvName` → the provider name
   - `pwszContainerName` → the key container
   - `dwProvType == 0` indicates CNG (a KSP) rather than a legacy CSP
4. Copy `pbCertEncoded` / `cbCertEncoded` into a Go slice. **Copy it.** The memory belongs to the store and is freed when the store closes.
5. `CertCloseStore` with `CERT_CLOSE_STORE_FORCE_FLAG`.

### 3.3 Certificates without a private key are skipped

If `CertGetCertificateContextProperty` returns `CRYPT_E_NOT_FOUND` (`0x80092004`) for the key-provider property, the certificate has no associated private key. Skip it silently. This is normal: CA certificates and imported public certificates live in the same store.

### 3.4 Deducing `OnHardware`

From the provider name:

| Provider | `OnHardware` |
|---|---|
| `Microsoft Smart Card Key Storage Provider` | **true** |
| `Microsoft Base Smart Card Crypto Provider` | true (legacy CSP path) |
| `Microsoft Software Key Storage Provider` | false |
| Anything else | false, and log the provider name at info level |

The unknown case is logged deliberately: if a certification authority ships its own KSP, we want to see the name in a user's log rather than guess.

### 3.5 What was measured on a real machine

Verified with `certutil -csplist` and `certutil -user -store My`:

- MUP and PKS both use **TrustEdgeID** (NetSeT) middleware; their certificates surface through `Microsoft Smart Card Key Storage Provider`.
- Halcom uses **Nexus Personal**, which registers a minidriver, so its certificates also surface through `Microsoft Smart Card Key Storage Provider`. Nexus additionally registers a legacy `Personal CSP`, which we ignore.
- **No vendor-specific KSP exists in the provider list.** Everything goes through Microsoft's.

> **Conclusion, and it simplifies this phase considerably: on Windows, CNG covers MUP, PKS and Halcom. PKCS#11 is not needed on Windows at all.**

Also observed on the same machine, and worth expecting in code: the store contained two Windows-internal certificates whose subject is a bare GUID, issued by themselves, on the software KSP. They must not appear in the certificate list. The classification step filters them out naturally (§5.4), but do not be surprised by them.

### 3.6 Tests

The Windows API layer cannot be unit-tested. The logic around it can:

- Provider-name-to-`OnHardware` mapping, as a table.
- Thumbprint computation from a known DER file in `testdata/certs/`, compared against a known value.
- `CRYPT_E_NOT_FOUND` results in a skipped certificate, not an error.

## 4. The Trusted List

**Package:** `internal/trust/tsl`

This is the most intricate part of the phase. Read it twice.

### 4.1 What the Trusted List is

The Republic of Serbia publishes an XML file conforming to **ETSI TS 119 612**. It lists every recognised trust service provider, each of their services, the certificate of each service, and the status of each service over time.

It is the authoritative answer to "is this certificate qualified". SPEC §11.1.

### 4.2 Structure you must parse

Root element `TrustServiceStatusList`, namespace `http://uri.etsi.org/02231/v2#`.

```
TrustServiceStatusList
├── SchemeInformation
│   ├── TSLSequenceNumber          integer, increases with each publication
│   ├── ListIssueDateTime          when it was issued
│   └── ...
├── TrustServiceProviderList
│   └── TrustServiceProvider  (repeated)
│       ├── TSPInformation
│       │   ├── TSPName/Name       provider name, several languages
│       │   └── TSPInformationURI
│       └── TSPServices
│           └── TSPService  (repeated)
│               ├── ServiceInformation
│               │   ├── ServiceTypeIdentifier    ends in /CA/QC, /TSA/QTST, /EDS/Q, ...
│               │   ├── ServiceName/Name
│               │   ├── ServiceDigitalIdentity/DigitalId/X509Certificate   base64 DER
│               │   ├── ServiceStatus            ends in /granted or /withdrawn
│               │   ├── StatusStartingTime
│               │   └── ServiceInformationExtensions
│               │       └── Qualifications/.../Qualifier uri=".../QCWithQSCD" etc.
│               └── ServiceHistoryInstance  (repeated, optional)
└── Signature   (XML-DSig, enveloped)
```

### 4.3 Facts about the current list, measured

- Sequence number **36**, issued **2026-05-20**.
- **11 providers.**
- Service type identifiers seen: `CA/QC`, `TSA/QTST`, `EDS/Q`, `PSES/Q`, `QESValidation/Q`.
- Statuses seen: `granted`, `withdrawn`.
- Qualifiers seen: `QCStatement`, `QCWithSSCD`, `QCWithQSCD`, `QCQSCDManagedOnBehalf`.
- **There are zero `ServiceSupplyPoint` elements.** OCSP and TSA endpoints cannot be obtained from the list. They come from the certificate's AIA extension or from configuration. Do not write code that looks for them.
- `ServiceHistoryInstance` elements exist (31 of them) and matter: a service that is `withdrawn` today may have been `granted` when a document was signed two years ago.

### 4.4 The service certificates you must be able to find

These are the trust anchors for the issuers we support. Your parser is correct when it finds all of them with status `granted`. SHA-256 fingerprints, shortened:

| MUP Gradjani CA 4 | `0E:3E:FE:B4:F7:7F:95:11…` |
| MUP Stranci CA 4 | `92:32:34:E9:38:2D:75:39…` |
| Pošta Srbije CA 1 | `20:EC:0D:B0:BC:17:1A:06…` |
| Pošta Srbije CA 2 | `91:38:F1:CF:70:B0:A1:9A…` |
| PKS CA Class1 – Kvalifikovani sertifikati | `F0:04:AB:5F:50:23:EF:ED…` |

### 4.5 Signature verification — the hard part

The list carries an **enveloped XML-DSig signature**. Verifying it requires **exclusive XML canonicalisation** (C14N 1.0 exclusive, without comments), which the Go standard library does not provide.

**Write it.** Sub-package `internal/trust/tsl/c14n`, with its own tests. It is roughly 300–500 lines and it is the only honest way to verify the list. Do not import an XML-DSig library — this code decides what the agent trusts, and it must be small enough to read.

Canonicalisation rules you must implement:

- Elements and attributes serialised in document order; attributes sorted by namespace URI then local name.
- Namespace declarations rendered only where **visibly utilised**, which is what makes it *exclusive*; inherited-but-unused declarations are dropped.
- Attribute values: `&` → `&amp;`, `<` → `&lt;`, `"` → `&quot;`, tab → `&#x9;`, newline → `&#xA;`, carriage return → `&#xD;`.
- Text nodes: `&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`, carriage return → `&#xD;`.
- Empty elements are written as start tag plus end tag, never self-closing.
- No XML declaration in the output.
- Whitespace outside the document element is dropped; whitespace inside is preserved exactly.

The enveloped-signature transform means: remove the `Signature` element itself, then canonicalise, then digest.

### 4.6 The signer certificates are pinned

The Ministry publishes two signing certificates. Embed both SHA-256 fingerprints in the binary and reject any signature by anything else:

```
Serbian Trusted List Signer 1  (valid to 2028-06-10)
cfd20b5a6696621266171c7cd3969bce23bbb2910ddf73bbf54e235d26b7e4b1

Serbian Trusted List Signer 2  (valid to 2028-12-31)
397e057c6d818feaa4e17154aeb88c2071ade2077520de42e092853e73336d2d
```

Both are self-signed, with subject `CN=Serbian Trusted List Signer N, O=Republic of Serbia, Ministry of Information and Telecommunications, organizationIdentifier=VATRS-113344563, C=RS`.

Pinning is deliberate. There is no chain to validate here, so a fingerprint comparison is both simpler and stronger.

### 4.7 Bundled seed list

Embed a known-good Trusted List in the binary with `//go:embed`, along with its SHA-256.

Why: on first run, on a machine with no network, the agent must still be able to say something truthful about a certificate. It loads the seed, marks it with its issue date, and displays its age.

The seed for this phase is sequence **36**, issued **2026-05-20**, SHA-256 `3f5744843bcfaba0698c6b5f7121ee9f133151249808c9de0ebb8e351d9ddb8b`. Verify that digest at build time in a test.

### 4.8 Refresh behaviour

```go
// Store holds the current Trusted List and keeps it fresh.
type Store interface {
    // Current returns the list in use, its issue date, and where it came
    // from. It never returns an error for a stale list — staleness is
    // reported, not treated as failure.
    Current(ctx context.Context) (*List, Provenance, error)

    // Refresh attempts to fetch a newer list. Failure is logged and
    // returned, but leaves the existing list in place.
    Refresh(ctx context.Context) error
}

type Provenance struct {
    Source    SourceKind  // Embedded, Cache, Network
    IssuedAt  time.Time
    FetchedAt time.Time
    Sequence  int
}
```

Rules:

- The download URL is **configurable**, with the Ministry's published address as the default.
- Refresh at startup and every 24 hours.
- A fetched list is accepted only if its signature verifies against a pinned certificate **and** its sequence number is **greater than or equal to** the current one. A lower sequence number is a rollback attempt: reject it and log a warning.
- On success, write to the cache directory atomically (temp plus rename).
- **Network failure is never fatal.** Log, keep the current list, carry on.
- The UI shows the list's age. Older than 30 days gets a visible warning; the agent still works.

### 4.9 Tests

- Parse the bundled list: assert 11 providers and that all seven service certificates from §4.4 are found with status `granted`.
- Canonicalisation: a table of small XML documents with known C14N output. Take test vectors from the W3C exclusive-C14N specification — do not invent your own.
- Signature verification against the bundled list must **succeed**.
- Flip one byte in the bundled list; verification must **fail**.
- Signature made by an unpinned certificate must be **rejected**.
- A list with a lower sequence number must be **rejected**.
- Network failure leaves the previous list intact and returns a stale provenance.
- `ServiceHistoryInstance` is parsed and a historical status can be resolved for a given date.

## 5. Classification

**Package:** `internal/trust/classify`

Turns raw DER into something the interface can display and the signing layer can trust. This is where SPEC §11 becomes code.

### 5.1 Output

```go
// Info is everything the agent knows about one certificate.
type Info struct {
    Thumbprint string
    Subject    Subject
    IssuerCN   string
    NotBefore  time.Time
    NotAfter   time.Time

    // Qualification is the result of the TSL check.
    Qualification Qualification

    // Purpose is derived from key usage: signing, authentication, or
    // unknown. This is what separates two certificates with identical
    // subjects (SPEC §11.5).
    Purpose Purpose

    // OnQSCD is true when the certificate asserts QcSSCD, or when the
    // TSL service carries a QCWithQSCD qualifier.
    OnQSCD bool

    // Usable is true when the certificate can be used to sign right now:
    // correct purpose, within validity, hardware present.
    Usable bool

    // NotUsableReason carries the error code explaining Usable == false.
    NotUsableReason errs.Code
}

type Qualification int
const (
    QualificationUnknown Qualification = iota
    QualificationQualified            // chain reaches a granted TSL service
    QualificationNotQualified
)

type Purpose int
const (
    PurposeUnknown Purpose = iota
    PurposeSigning         // contentCommitment set
    PurposeAuthentication  // digitalSignature/keyEncipherment, no contentCommitment
)
```

### 5.2 Purpose — get this right or Halcom breaks

SPEC §11.4, measured:

| Issuer | KeyUsage on the signing certificate |
|---|---|
| MUP | `digitalSignature` + `contentCommitment` |
| Pošta | `digitalSignature` + `contentCommitment` |
| **Halcom** | **`contentCommitment` only** |

```go
// Purpose is decided by contentCommitment alone. Halcom's signing
// certificates do NOT set digitalSignature; a filter requiring it rejects
// every Halcom certificate (SPEC §11.4).
if ku.ContentCommitment {
    return PurposeSigning
}
if ku.DigitalSignature || ku.KeyEncipherment {
    return PurposeAuthentication
}
return PurposeUnknown
```

In Go's `crypto/x509`, `contentCommitment` is `x509.KeyUsageContentCommitment`. It is the same bit historically called `nonRepudiation`.

### 5.3 Subject parsing — three traps

```go
type Subject struct {
    // DisplayName is built from givenName + surname, never from CN.
    DisplayName string

    GivenName string
    Surname   string

    // CommonName is kept raw for technical display.
    CommonName string

    // Organisation and its identifiers, when present.
    Organisation string
    TaxID        string  // from "VATRS-..."
    CompanyID    string  // from "MB:RS-..."

    // IssuerAssignedID is the CA's internal reference, from "CA:RS-...".
    // It is NOT the national identity number.
    IssuerAssignedID string

    Country  string
    Locality string
}
```

**Trap 1 — multi-valued RDNs.** Attributes appear twice inside a *single* RDN:

```
2.5.4.5  = CA:RS-246275 + 2.5.4.5  = PNORS-2003964710097
2.5.4.97 = MB:RS-17491857 + 2.5.4.97 = VATRS-103026255
```

`crypto/x509` flattens `Subject.Names` into a list of `AttributeTypeAndValue`, so both values are reachable — but a naive "find the first `2.5.4.5`" returns one of them non-deterministically. **Iterate every entry and dispatch on the value's prefix**, not on the attribute type alone.

```go
for _, atv := range cert.Subject.Names {
    if atv.Type.Equal(oidSerialNumber) {   // 2.5.4.5
        v, _ := atv.Value.(string)
        switch {
        case strings.HasPrefix(v, "CA:RS-"):
            s.IssuerAssignedID = strings.TrimPrefix(v, "CA:RS-")
        case strings.HasPrefix(v, "PNORS-"), strings.HasPrefix(v, "PNORS"),
             strings.HasPrefix(v, "IDCRS-"), strings.HasPrefix(v, "PAS"):
            // National identity number, ID card number or passport
            // number. Personal data — deliberately discarded (SPEC §11.6).
        }
    }
}
```

Getting this wrong is the easiest way to put a national identity number where an internal reference number belongs, and from there into a visual stamp on a document sent to a third party.

**Trap 2 — the national identity number is present in all three issuers.** As `PNORS-<13 digits>`. Halcom additionally uses `IDCRS-<ID card number>` and `PAS<CC>-<passport number>`. Strip all of them; never store any in `Info`.

**Trap 3 — the email address is in two different places.**

| Issuer | Location |
|---|---|
| Halcom | `emailAddress` (`1.2.840.113549.1.9.1`) **inside the Subject DN** |
| MUP, Pošta | `rfc822Name` in **SubjectAlternativeName** |

Neither is stored in `Info` and neither is ever logged.

**CN is not a name.** Real values:

```
"ВЕЉКО СТАНОЈЕВИЋ 011445479 Sign"      Cyrillic, CA number, literal " Sign"
"Zoran Milovanović 246275"
"Redžvel Mešković 200094362"
```

Do not write a regex. All three carry `givenName` (2.5.4.42) and `surname` (2.5.4.4) separately. `DisplayName = GivenName + " " + Surname`. If either is missing, fall back to raw CN and log it — do not attempt to clean CN up.

### 5.4 Qualification

Primary test, per SPEC §11.1:

1. Build the chain from the certificate towards a root. In F1, use only what is available: the certificate's own issuer name and the TSL service certificates. **Do not fetch AIA over the network in this phase** — chain completion arrives in F3, where it is needed for the output document.
2. If the issuer matches a TSL service certificate whose type is `CA/QC` and whose status was `granted` at the current time, the certificate is **qualified**.
3. Otherwise **not qualified**.

Supporting signals, recorded for display but never used as the primary test:

```go
// eIDAS policy OID present on all three issuers' end-entity certificates.
const oidQCPnQSCD = "0.4.0.194112.1.2"   // QCP-n-qscd

// qcStatements (extension 1.3.6.1.5.5.7.1.3)
const (
    oidQcCompliance = "0.4.0.1862.1.1"
    oidQcSSCD       = "0.4.0.1862.1.4"
    oidQcPDS        = "0.4.0.1862.1.5"   // Halcom only
    oidQcType       = "0.4.0.1862.1.6"
    oidQcTypeESign  = "0.4.0.1862.1.6.1"
    oidQcTypeESeal  = "0.4.0.1862.1.6.2"
)

// PKIXQCSyntax-v2 with a natural-person semantics identifier.
const (
    oidPKIXQCSyntaxV2  = "1.3.6.1.5.5.7.11.2"
    oidSemanticsNatural = "0.4.0.194121.1.1"
)
```

Issuer-specific policy OIDs, for display only:

| Issuer | OID |
|---|---|
| MUP | `1.3.6.1.4.1.33589.1.1.0` |
| Pošta | `1.3.6.1.4.1.15672.10.142.1.0` |
| Halcom (legal-person branch) | `1.3.6.1.4.1.5939.10.1.6` |

> **Do not populate this table from vendor documentation.** Halcom's published policy document states `1.3.6.1.4.1.5939.11.2.6`; the actual certificate contains `1.3.6.1.4.1.5939.10.1.6`. SPEC §11.3.

`qcStatements` is not parsed by `crypto/x509`. Read the raw extension and decode it yourself:

```go
type qcStatement struct {
    StatementID asn1.ObjectIdentifier
    Info        asn1.RawValue `asn1:"optional"`
}
// The extension value is a SEQUENCE OF QCStatement.
```

The Windows-internal certificates mentioned in §3.5 — self-signed, GUID subject, software KSP — fall out here as `QualificationNotQualified` with `PurposeUnknown`, and are therefore hidden from the default list.

### 5.5 Usability

```go
// Usable answers "can this certificate sign right now".
func computeUsable(info Info, hardwarePresent bool, onHardware bool) (bool, errs.Code) {
    if info.Purpose != PurposeSigning {
        return false, errs.CodeCertNotUsable
    }
    now := time.Now()
    if now.Before(info.NotBefore) || now.After(info.NotAfter) {
        return false, errs.CodeCertExpired
    }
    if onHardware && !hardwarePresent {
        return false, errs.CodeCardNotPresent
    }
    return true, ""
}
```

Revocation checking is **not** part of F1. It requires network calls and arrives in F3 where the result must be embedded in the document.

### 5.6 Tests — the important ones

Place real DER certificates in `testdata/certs/`, extracted from signed documents. **No private keys.** These are public certificates from real documents and contain personal data, so:

- store only the three issuer certificates and the CA certificates needed for chain tests
- add a `testdata/certs/README.md` explaining their provenance and that they must never be regenerated from a live card

Required tests:

| Test | Asserts |
|---|---|
| Halcom signing certificate | `Purpose == PurposeSigning` **despite `digitalSignature` being absent** |
| Halcom authentication certificate | `Purpose == PurposeAuthentication`, same subject as the signing one |
| Two Halcom certificates | Identical `Subject` structs, different `Thumbprint`, different `Purpose` |
| MUP certificate | `DisplayName` is the Cyrillic name without the trailing number and without `" Sign"` |
| All three issuers | `IssuerAssignedID` is the `CA:RS-` value, **never** the `PNORS-` value |
| All three issuers | No field of `Info` contains 13 consecutive digits |
| All three issuers | No field of `Info` contains `"@"` |
| All three issuers | `Qualification == QualificationQualified` against the bundled TSL |
| Self-signed test certificate | `QualificationNotQualified` |
| Expired certificate | `Usable == false`, `NotUsableReason == CodeCertExpired` |
| Hardware certificate, no card | `Usable == false`, `NotUsableReason == CodeCardNotPresent` |

The two "no 13 digits" and "no @" tests are worth more than they look. They are cheap, they are unambiguous, and they will catch a regression that no reviewer would notice.

## 6. The `certs` command

**Package:** `internal/cli`

### 6.1 Behaviour

```
$ liro-bridge certs
```

Output, human-readable and localised:

```
Readers: 1
  Generic Smart Card Reader Interface 0 — card present

Certificates: 1

  [1] ВЕЉКО СТАНОЈЕВИЋ                                    ✓ usable
      Purpose      signing
      Issuer       MUP Gradjani CA 4
      Qualified    yes — qualified certificate on a QSCD
      Valid        2021-09-23 to 2026-09-24
      Thumbprint   …B3D1ECCE
      Storage      smart card

Trusted List: sequence 36, issued 2026-05-20 (103 days old, from cache)
```

> **Amended (F6b, "one window"):** the listing above once carried a
> second entry — the authentication certificate on the same card, shown
> and disabled with the reason "certificate cannot be used for
> signing", under a `Certificates: 2` header. It is hidden now, and
> the count above has been corrected with it.
>
> The reasoning for showing it was that hiding it would make a user
> think their card was broken. That was wrong about what a person
> actually sees. Every Serbian card carries an authentication
> certificate beside the signing one, and on a Halcom card their
> Subject DN is byte-for-byte identical (SPEC §11.5) — so the list
> showed the person their own name twice, the second time struck
> through, under a sentence about a distinction they have no vocabulary
> for. It is not a choice.
>
> What is still shown, and still disabled with its reason, is a
> *signing* certificate that cannot be used right now: an absent card,
> an expired certificate. Those are real choices temporarily
> unavailable, and hiding *them* is what would make a card look broken.
> See docs/decisions.md.

Flags:

- `--json` — machine-readable output, same data, for scripting and testing.
- `--all` — include certificates hidden by default (anything that is not a signing certificate, and Windows-internal artefacts).

### 6.2 Requirements

- **The thumbprint is shown as the last 8 characters**, which is what distinguishes two certificates with identical subjects (SPEC §11.5). It appears on every row without exception.
- The Trusted List age is always shown. Over 30 days gets a visible warning.
- No reader attached produces a calm `Readers: none attached`, not an error.
- Every user-visible string comes from the i18n catalogue. Add the required keys to all three locale files; the completeness test from F0 will enforce it.
- Certificate subject data is displayed in its own script — a Cyrillic name stays Cyrillic even when the interface is English (SPEC §9.3).

## 7. What must not happen in this phase

- **No private key is used.** No PIN prompt appears at any point. If your code triggers one, something is calling a signing API that does not belong here.
- **No network call except the TSL refresh.** No OCSP, no AIA fetching, no CRL.
- **No `internal/api`, no `internal/ui`, no `internal/pades`.** Those directories stay empty.
- **No presence detection from the certificate store.** SPEC §18.13.

## 8. Decisions to record

At minimum, in `docs/decisions.md`:

- **D-006** — Qualification is decided by the Trusted List, with policy OIDs and `qcStatements` as supporting evidence only. Rejected: OID-only heuristics, because vendor documentation of OIDs was found to be wrong and because only the list carries status over time.
- **D-007** — Presence is detected via `SCardListReaders` and reader state, never from certificate enumeration. Include the measurement: certificates enumerate normally with an empty reader.
- **D-008** — Purpose is decided by `contentCommitment` alone. Include the measurement: Halcom omits `digitalSignature`.
- **D-009** — Exclusive C14N is implemented in-house rather than imported. Reasoning: this code decides what the agent trusts and must be small enough to audit.
- **D-010** — TSL signer certificates are pinned by SHA-256 rather than chain-validated. Reasoning: they are self-signed, so there is no chain; a fingerprint is simpler and stronger.
- **D-011** — A Trusted List is bundled as a seed so a first run with no network still produces a truthful answer.
- **D-012** — Display names are built from `givenName` + `surname`, not parsed out of CN. Include the three real CN values as evidence.
