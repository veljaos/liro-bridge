# Phase F5 — The agent

**Prerequisite reading:** `docs/SPEC.md` in full, with §6 (security model), §9 (internationalisation) and §10 (visual design) as the core of this assignment, then `docs/decisions.md` in full.

**Prerequisite phase:** F4 complete.

**Goal of this phase:** Liro Bridge becomes a program a person uses. It lives in the system tray, shows a consent window when a signature is requested, signs, and writes a tamper-evident audit entry.

**This phase has the most unknowns of the remaining three.** WebView2 has no official Go binding and must be driven through COM by hand. Budget for that.

**Explicitly not in this phase:** no HTTP server, no drag and drop, no shell integration. The consent flow is triggered from the CLI in this phase; F6 and F7 supply the real callers.

**Exit condition:** a person runs `liro-bridge sign --interactive`, a window appears, they choose a certificate and press Approve, the card asks for a PIN, the document is signed, and an audit entry is written.

---

## 1. What gets built

1. **WebView2 host** — creating, sizing and driving a window from Go.
2. **Tray icon** with a small menu.
3. **Token pipeline** — generating `tokens.css` from the design system.
4. **Three windows** — consent, pairing, settings.
5. **Audit log** with a hash chain.

Build in that order. The window host is the risky part; get it working with a blank page before designing anything.

---

## 2. The WebView2 host

**Package:** `internal/ui`

### 2.1 Reality check

WebView2 is a COM API. From Go this means `syscall`, manual vtable dispatch, and careful lifetime management. There is no supported binding.

**Two approaches are acceptable.** Choose one, record the choice with reasoning:

- Hand-written COM interop in `internal/ui`, consistent with how F1 and F2 handled `winscard` and `crypt32` — pure logic separated from DLL glue, testable on any OS.
- A single well-scoped third-party binding, if one exists that is maintained and small enough to read. SPEC §8.6 requires recording what it does, why the standard library is insufficient, and its licence.

Prefer the first if the second means importing something large.

### 2.2 Runtime dependency

WebView2 requires the Evergreen Runtime, which is present on current Windows 11 and most Windows 10 installations, but not all.

**If it is absent, the agent must not crash and must not fail silently.** Detect it at startup and show a native `MessageBox` explaining what is missing and where to get it. Record the detection method.

This matters because the target user is a bookkeeper on a machine they do not administer.

### 2.3 Window basics

- Fixed size, not resizable. The consent window is 480 × 420 points; settings 520 × 480. Content is designed to fit.
- Centred on the display containing the cursor, not always the primary display.
- **DPI-aware.** Declare per-monitor DPI awareness in the manifest and handle `WM_DPICHANGED`. Without it the window is blurry on a scaled display, which is most laptops.
- The consent window is **always on top** and takes focus when shown. A consent request the user does not see is a consent request that times out.
- Closing the window is equivalent to Cancel.

### 2.4 Go ↔ JavaScript

Two directions:

- **Go → page:** `ExecuteScript` with a JSON payload. Never build JavaScript by string concatenation with user data in it.
- **Page → Go:** `AddScriptToExecuteOnDocumentCreated` plus `WebMessageReceived`. Messages are JSON with a `type` field and are validated in Go before anything is acted on.

The page is loaded from embedded assets over a virtual host mapping, not from `file://` and not from a local HTTP server. A local server would be a second listening socket, which contradicts the security model.

**The page can request exactly three things:** approve, cancel, and select a certificate by thumbprint. Anything else is dropped and logged. Keep the message surface this small deliberately.

## 3. Tray

- Icon in the notification area, present from startup.
- Left click opens the main window (in this phase, a placeholder; F6 fills it).
- Right click gives a menu: Open, Settings, Certificates, View audit log, Quit.
- Tooltip shows the version.
- **The agent starts minimised to tray with no window.** SPEC's product shape: it is invisible until it is needed.

Autostart via `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, controlled by a setting, defaulting to on. `HKCU`, never `HKLM` — no administrator rights.

## 4. Design tokens

### 4.1 The pipeline

`@liro/tokens` generates a `tokens.css` containing every colour, spacing and typography value as CSS custom properties. That file is embedded in the agent and is the only source of visual values.

Add `scripts/synctokens` which pulls the generated `tokens.css` and the intent classes into `internal/ui/assets/`. Commit the output so builds are reproducible without the design system present.

### 4.2 The rule that keeps it honest

**A hex colour literal anywhere in the agent's CSS fails the build.** Not a warning. Add the check to `scripts/checkdeps` or a sibling script, and give it a test that makes it fire — the same discipline that caught the dependency-rule bug in F0 and the xref bug in F3.

If a needed value has no token, add a token. Do not write the hex.

## 5. The consent window

This is the security boundary of the entire product. SPEC §6.5: the PIN is cached by the card independently of our process, so **the human pressing Approve is the only thing that reliably prevents an unauthorised signature.**

### 5.1 Layout priorities

The person doing this for the thirtieth time today does not read; they recognise a shape. Design for that.

**Prominent, read in under two seconds:**

- Who is signing — the signer's name, largest text on the screen
- How many documents
- One obvious primary action

**Secondary, present but quieter:**

- Which application is asking
- Certificate issuer and the last 8 characters of the thumbprint
- Qualified status

**Behind a "Details" disclosure, collapsed by default:**

- Batch fingerprint
- Full file list
- Signature level, timestamp authority, policy OIDs

Everything the engine knows is available. Almost none of it is on the first screen.

### 5.2 Certificate selection

SPEC §11.5: two certificates on one card can have byte-identical subjects. And a bookkeeper's machine commonly holds several clients' certificates.

Requirements:

- Every row shows the display name, the role derived from key usage ("for signing" / "for login"), the issuer, and **the last 8 characters of the SHA-1 thumbprint**. The thumbprint is not optional; it is sometimes the only difference.
- ~~Non-signing certificates are shown disabled with the reason, not hidden. Hiding them makes the user think the card is broken.~~ **Superseded (F6b, "one window"):** a certificate that is not for signing is hidden; only a *signing* certificate that cannot be used right now is shown disabled with its reason. See SPEC §11.5, F1 §6.1 and docs/decisions.md.
- **No "remember this certificate".** Selection is explicit every session. SPEC §18.15.
- Test-key certificates from the soft token carry a loud, unmissable marker.

### 5.3 File names are untrusted input

SPEC §6.6. Names arrive from a potentially hostile caller.

- Insert with `textContent`, never `innerHTML`.
- Truncate at 120 characters with the middle elided: `long-start…long-end.pdf`.
- **Strip control characters and Unicode direction overrides** — `U+202A`–`U+202E` and `U+2066`–`U+2069`. These make `racun\u202Efdp.exe` display as `racun exe.pdf`.
- Show at most 10 names, then "…and N more".
- Never treat a name as a path. Display only.

The application name shown is the one **bound at pairing time**, never one supplied in the request.

Write a test with a malicious name containing a right-to-left override and assert the rendered output is neutralised.

### 5.4 The first five seconds

Measured: the first signature takes about 4.9 seconds of card initialisation. An unmoving progress bar for five seconds reads as a freeze, and the user clicks again.

Required states, in order:

| State | Shown |
|---|---|
| Waiting for approval | the summary and the buttons |
| Preparing card | **"Preparing card…"**, indeterminate, no numbers, no percentage |
| Signing | "Signing 7 of 100", determinate bar, ETA computed from the measured first signature |
| Done | count succeeded, count failed, path to the output |
| Failed | what happened and what to do about it |

If the PIN policy is detected as per-signature (F2), change the message to warn that the PIN will be requested repeatedly.

### 5.5 Errors say what to do

The agent returns codes; the UI translates them into an action.

| Code | What the user sees |
|---|---|
| `CARD_NOT_PRESENT` | "Insert your card into the reader." |
| `NO_READER` | "No card reader detected. Connect the reader and try again." |
| `PIN_INCORRECT` | "Incorrect PIN. Attempts remaining before the card is blocked are limited." |
| `PIN_LOCKED` | "The card is blocked. Unblock it with your PUK using your issuer's software." |
| `TSA_UNAVAILABLE` | "The timestamp service is not responding." with the choice from SPEC §12.8 |
| `SMART_CARD_SERVICE_DOWN` | "The Windows Smart Card service is not running." |

**No error code appears in the interface.** Codes go in the log, where developers read them. A "Copy technical details" button on the error state is fine and useful.

### 5.6 Accessibility

Full keyboard navigation. Visible focus ring using the token colour.

**Approve is not the initially focused control.** The user must move to it deliberately. A consent dialog where Enter immediately approves is not consent.

Escape cancels.

## 6. Pairing window

Simpler. Shows the requesting application's name and origin **verbatim**, with the same untrusted-input handling as file names, and Allow / Deny.

The origin is displayed unmodified — no prettifying, no stripping of the scheme. A user who sees `http://` instead of `https://` should be able to notice.

In this phase the window exists and is testable; the protocol that drives it arrives in F7.

## 8. Audit log

**Package:** `internal/audit`

### 8.1 Entry

```go
type Entry struct {
    Sequence     uint64
    Timestamp    time.Time
    Thumbprint   string   // SHA-1 of the signing certificate
    Application  string   // as bound at pairing, or "local"
    DocumentCount int
    Outcome      Outcome  // approved, denied, failed, partial
    FailureCode  errs.Code
    IsTestKey    bool
    PrevHash     []byte   // SHA-256 of the previous entry's canonical form
    Hash         []byte
}
```

### 8.2 The hash chain

Each entry's hash covers its own canonical serialisation **and** the previous entry's hash. Removing or altering an entry breaks every entry after it.

The canonical form must be stable across versions — define it explicitly (field order, encoding) and test that it does not change.

Provide `audit verify` which walks the chain and reports the first break.

### 8.3 What never goes in

SPEC §6.7. **Never:** the national identity number, email addresses, file names, document contents, personal names.

Note that personal names are excluded even though they appear on the consent screen. The certificate thumbprint identifies the signer without storing their identity.

Write a test that runs a full batch with a Cyrillic-named certificate and malicious file names, then asserts the resulting log contains no `@`, no 13-digit run, and none of the file names.

### 8.4 Storage

`%LOCALAPPDATA%\Liro\audit\`, one file per month, rotated by size at 5 MB. Never uploaded. Export on user request writes a copy plus a verification report.

## 10. Tests

Window code cannot be unit-tested. Structure so that everything else can:

- **View models.** The consent screen's data — what is prominent, what is behind Details, which certificates are disabled and why — is computed in Go and testable without a window.
- **Sanitisation.** Direction overrides, control characters, truncation, the 10-name cap. Table-driven.
- **Message validation.** Malformed messages from the page are rejected. Unknown types are dropped and logged.
- **State machine.** Waiting → preparing → signing → done, and every failure path.
- **Audit chain.** Append 100 entries, verify; alter entry 50, assert verification reports break at 50; delete entry 30, assert the same.
- **Audit privacy.** The test from §8.3.
- **CSS token check.** A hex literal in agent CSS fails the build, proven by a test.
- **Locale rendering.** All three, with the expected strings.

### 10.1 Manual acceptance

- Card in reader: approve, PIN, signature, audit entry written.
- Cancel: `CONSENT_DENIED`, no signature, audit entry recorded as denied.
- Card absent: the message says to insert the card, not a code.
- Reader unplugged mid-batch: clean abort with an actionable message.
- 100 documents: one PIN, "Preparing card…" for the first five seconds, then a moving bar with a sensible ETA.
- Two certificates with identical subjects: distinguishable in the list by role and thumbprint.
- Scaled display at 150%: the window is sharp, nothing is clipped.
- Cyrillic interface: everything renders, nothing overflows.
- WebView2 runtime absent: a clear message, not a crash.
